# STAGE-009-016: Whole-folder + markdown drift hash

## Status: Complete

## Overview

Extend `runbooks.content_hash` (currently YAML-only, per STAGE-009-001) to hash the entire runbook folder including `*.md` files and any sibling files. This closes the drift-detection gap owed by STAGE-009-001 and STAGE-009-006: currently a user editing `README.md` or auxiliary scripts under a runbook folder does NOT invalidate a pinned dry-run approval, which weakens non-negotiable #4 (content_hash must reflect the authoritative content used by the run).

**Deferred from:** STAGE-009-012 Design (2026-07-03). Origin regression items filed under STAGE-009-001 and STAGE-009-006.

## Design Notes

**Selected by:** implementing session (autonomous loop). Brainstormer (Opus) presented options; coordinator selected recommended picks. Rationale keyed to non-negotiable #4 (audit immutable + content_hash reflects the AUTHORITATIVE content the runbook actually uses).

### Hash algorithm — Option A (sorted-path serialization + single SHA-256)

New signature: `compute_runbook_content_hash(folder: Path) -> str` (drops the config param — folder is the authoritative input; the loader already located it).

Algorithm:
1. Enumerate the folder recursively via byte-wise `sorted()` on `Path.as_posix().encode()` (NOT locale-aware sort — deterministic across containers).
2. For each file, feed a SHA-256 hasher: `path_bytes + b"\x00" + str(size).encode() + b"\x00" + content_bytes + b"\x00"`. The `path\x00size\x00content\x00` framing prevents move-between-files collision classes (same content, different path → different hash).
3. Text files (allowlist below): normalize CRLF → LF on content before hashing.
4. Return `f"v2:sha256:{hasher.hexdigest()}"` — the `v2:` prefix is a permanent audit-clarity marker for archaeology across the deploy transition (v1 hashes have no prefix; v2 hashes always do). `runbook_runs.runbook_hash` rows written after this stage will forever be distinguishable from pre-stage rows.

Exclusions / hard rejects (fail-loud posture — errors surface at `POST /api/runbooks/refresh` time as a per-folder error, not silent skip):
- **Text file extension allowlist:** `.md .yaml .yml .sh .txt .json .toml`. Any other file extension → hard reject ("unexpected file type in runbook folder").
- **Symlinks:** hard reject.
- **Non-ASCII filenames:** hard reject (macOS APFS NFD vs Linux ext4 normalization would otherwise silently drift the hash across dev/prod).
- **File size > 1 MiB:** hard reject.
- **File count > 50 per folder:** hard reject.
- **`runbook.yaml` bytes are hashed as raw bytes** (not `model_dump`). Semantically-equivalent-but-textually-different edits (comment changes, whitespace, key reordering) NOW invalidate the hash — the current YAML-model hash was too permissive relative to non-negotiable #4.

Explicitly NOT in the hash:
- Folder name / path (DB row is keyed by folder path; renaming = delete-row-then-insert-row on next refresh, which is already the invalidation path).

### Backfill — Option B (lazy backfill on next `POST /api/runbooks/refresh`)

No data migration. The existing `RunbookRepo.reconcile` flow at `apps/monitor/homelab_monitor/kernel/runbooks/repository.py:159` is the exclusive writer of `runbooks.content_hash`; it will recompute using the new hash function on the first refresh after deploy. Rows whose folders no longer exist on disk are already handled by the existing reconcile logic.

Rationale for choosing B over an Alembic migration:
- Migrations should be schema+data operations against the DB, not filesystem-dependent side effects. An Alembic migration that imports application code AND depends on the `/runbooks` bind-mount being present is a category to avoid on principle.
- Non-determinism window is theoretical: refresh is the first operator action after any deploy anyway (to confirm runbooks loaded), and pre-deploy pinned approvals will 409 on approve either way (that's the design).
- B reuses the tested reconcile code path (folder-missing handling, audit emission, transaction shape) instead of duplicating it inside a migration.

Post-deploy operator step (added by Build phase to `docs/dev/local-environment.md` or a new deploy checklist): "After deploying STAGE-009-016, call `POST /api/runbooks/refresh` to backfill content hashes to v2."

### Migration this stage still needs

Only a schema-touching migration is required IF we choose to add a CHECK constraint on the hash column format (`v2:sha256:<hex>`). **Decision: no CHECK constraint.** The prefix is convention-only; keeping the column as TEXT NULL preserves audit-column immutability for pre-v2 rows in `runbook_runs.runbook_hash`. **No migration `0052` is created by this stage.** Next migration slot remains open.

### Expected behavior change (documented, NOT silent)

On first `POST /api/runbooks/refresh` after deploy:
- Every existing `runbooks` row with a folder still on disk gets its `content_hash` rewritten from a bare 64-hex string (v1) to `v2:sha256:<hex>`.
- Every pending `runbook_run_approvals` row's `pinned_runbook_hash` (a bare 64-hex v1 string) will unconditionally not match the recomputed v2 hash.
- Next `POST /autofix/approvals/{id}/approve` on any such row returns `409 runbook_changed_since_plan` — recorded as `autofix.rejected` audit event with `pinned_runbook_hash` (v1) and `current_runbook_hash` (v2) — the 409 IS the audit trail.
- `GET /api/autofix/approvals` will show `drift_detected: true` on every pending approval captured before the deploy (via `_drift_for` at `autofix.py:185`) — this is the UI's early warning to re-capture.

### Test plan (implemented in Build)

1. **README drift → 409:** create runbook folder with `runbook.yaml` + `CLAUDE.md` + `README.md`; POST refresh → hash captured. Insert a pending approval pinning the hash. Mutate `README.md`. POST refresh → hash changes. POST approve → 409 `runbook_changed_since_plan`.
2. **Sibling add/remove → hash changes:** add a `.txt` sibling → new hash; remove it → back to original hash. Deterministic add-remove reversibility.
3. **Deterministic across identical folder copies:** create two identical folders in different tmpdir paths → SAME hash (folder path is NOT in the hash input).
4. **v2 prefix present:** `assert hash.startswith("v2:sha256:")`.
5. **YAML raw-bytes vs model:** mutate `runbook.yaml` in a semantically-equivalent way (add a trailing comment, reorder keys) → hash CHANGES (v1 would have said no-change — v2 says change; documents the tighter surface).
6. **Line-ending canonicalization:** file with CRLF vs LF (same content) → SAME hash.
7. **Hard rejects fail cleanly:** symlink, non-ASCII filename, oversize file (>1 MiB), too many files (>50), non-allowlisted extension → refresh returns a per-folder error; existing folders continue to reconcile.
8. **Empty-folder-except-allowlisted-two:** `runbook.yaml` + `CLAUDE.md` only → produces a stable, tested-once-frozen expected hash (guards against future accidental skip of `CLAUDE.md`).
9. **Line-ending canonicalization applies only to text-allowlist extensions:** included file `.sh` with CRLF → LF-normalized; not that this stage supports binary files at all (they hard-reject), but the branch matters for coverage.
