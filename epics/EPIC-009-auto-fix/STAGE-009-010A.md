# STAGE-009-010A: Auto-fix UI — manual "Run fix" trigger (backend endpoint + UI button + risky-PATCH defense-in-depth)

## Status: Complete

## Overview

Build the operator-initiated manual-trigger surface deferred from STAGE-009-010. Adds a backend endpoint (`POST /api/runbooks/{id}/trigger` or equivalent) that lets an authenticated operator kick off a runbook against a synthetic operator-initiated alert (no real alert required), honoring ALL seven non-negotiables (allow-list, rate-limit, cooldown, kill-switch, risky→dry-run+approval, audit, identity). Adds a per-card "Run fix" button + Dialog modal to STAGE-009-010's Runbooks catalog cards (dry-vs-real toggle FORCED to dry for risky, confirm-on-destructive for real via ConfirmPhraseDialog). Also adds a defense-in-depth backend rejection of `PATCH /api/runbooks/{id}` when the request tries to set `auto_trigger=true` on a `risky` runbook (today the safety net is exec-time only via `dry_run_required` — the PATCH itself is permitted).

**Vertical slice:** after this stage, a user browsing `/runbooks` can click "Run fix" on any card, choose dry/real (locked to Dry for risky), confirm-on-destructive if real, and see the resulting run appear in the pending-approvals panel (for risky/dry) or as a real-run outcome (for safe/real). Desktop + Mobile viewport sign-off.

## Concrete deliverables

### 1. Backend trigger endpoint

`POST /api/runbooks/{id}/trigger` (auth + CSRF). Request body: `{ mode: "dry" | "real" }` (mode required; server rejects real for risky runbooks with 400 `dry_run_required_for_risky` even if UI lockout is bypassed). Response: `{ run_id, outcome, denial_reason?, real_run_id?, approval_id? }`. Errors: 409 with codes `kill_switch`, `rate_limit`, `cooldown`, `already_running`, plus 400 `dry_run_required_for_risky`, 404 `runbook_not_found`, 409 `runbook_disabled`.

### 2. Backend defense-in-depth for risky PATCH

`PATCH /api/runbooks/{id}` rejects requests that would set `auto_trigger=true` while `risk_tag=='risky'` (returns 400 with code `risky_auto_trigger_denied`). Matches the frontend info-tooltip semantic from STAGE-009-010.

### 3. Frontend Run-fix button + modal

Per-catalog-card "Run fix" button (STAGE-009-010's card layout). Radix Dialog modal shows: runbook name, mode radio (Dry / Real; Real disabled for risky with inline explanation), confirm-on-destructive via ConfirmPhraseDialog if Real, submit button. On dry-run success: closes modal, invalidates pending-approvals query so the new approval appears in 010's panel. On real-run success: closes modal, shows toast with outcome + run_id.

### 4. Audit surface

`initiated_by='operator'` recorded on operator-triggered `runbook_runs` rows; audit_log rows include the user identity.

### 5. Tests + sign-off

Backend pytest: kill-switch denial, rate-limit denial, cooldown denial, already-running denial, risky→real rejection, risky→dry produces approval, safe→real runs, 401/403, PATCH risky auto_trigger rejection. Vitest: modal opens from Run-fix button; risky card's Real radio is disabled; typed-phrase confirm required for real; error toasts render denial reasons. Desktop + Mobile viewport sign-off.

## Design Phase

### Design Notes (2026-07-02)

**Design authority:** Autonomous loop — options explored via a `brainstormer` (Opus); the implementing session selected the recommended options (per HANDOFF-NEXT.md §2 and the epic-loop autonomous-Design directive).

**Context verified against real code:** `apps/monitor/homelab_monitor/kernel/autofix/orchestrator.py` (`handle_alert` at :176; `_check_operational_gates` gate order at :208-237), `apps/monitor/homelab_monitor/kernel/api/routers/runbooks.py` (routes at :102, :111, :127), `apps/monitor/homelab_monitor/kernel/runbooks/repository.py` (`patch_gates` at :279-345), `apps/monitor/homelab_monitor/kernel/autofix/runs_repository.py` (`insert_started` at :84-114). `runbook_runs.alert_id` is ALREADY nullable per migration 0045 (only the Python signature of `insert_started` restricts it to `str`); `initiated_by` column does NOT exist today.

#### Decision A — Endpoint path + entry-point shape

**Chosen:** `POST /api/runbooks/{runbook_id}/trigger` + a NEW orchestrator public method `handle_operator_trigger(runbook_id, mode, principal, ip) -> RunResult`.

- **Endpoint path**: co-located with the runbook resource (mirrors the existing `PATCH /runbooks/{id}` pattern). Alternative `POST /api/autofix/trigger` was rejected as less REST-natural (trigger is scoped to a specific runbook, so the URL should say so).
- **Entry-point**: NEW public method rather than reusing `handle_alert` with a synthetic operator-alert. Synthetic-alert reuse (A3) was rejected because it conflates two different trust models behind one function — any future change to `handle_alert`'s match phase could silently change operator behavior on the highest-blast-radius epic in the project.
- **Refactor**: `_check_operational_gates(record)` extended to `_check_operational_gates(record, *, require_auto_trigger: bool = True)`. When `False` (operator path), the `auto_trigger` allow-list check is SKIPPED but every other gate (kill-switch FIRST, `record.enabled`, rate-limit, cooldown) is still enforced.
- **Signature widening**: `_claim_and_store_dry(alert, record)` and `_claim_and_exec(alert, record, ...)` widened to accept `alert: Alert | None`; when None (operator path), `insert_started` receives `alert_id=None` (the DB column is already nullable per migration 0045; only the Python signature needs widening — no migration required for this widening).
- **Rationale**: honors non-negotiable #1 (Trigger allow-list) by making the operator surface a first-class, separately-tested path; keeps `handle_alert` and its match-by-alert contract undisturbed.
- **Trade-off**: two similar-but-distinct gate sequences must be kept in sync via the `require_auto_trigger` flag; this is a real DRY cost accepted in exchange for path-clarity.

#### Decision B — Risky→real request behavior

**Chosen:** Server 400-rejects `mode='real'` requests for risky runbooks (`record.dry_run_required=True`) with code `dry_run_required_for_risky`, BEFORE any exec or lock claim. Silent-route-to-approval (B2) was rejected.

- **Rationale**: non-negotiable #5 says risky MUST require dry-run + manual approval — that's an explicit contract, not a silent transformation. Defense-in-depth means visible rejection at the API boundary, so any client (UI, curl, future CLI, future integration test) that bypasses the UI Real-radio lockout gets a clear, documented rejection. B2 would produce an approval a client didn't request and might not check.
- **Preserves the property**: response outcome matches requested mode, or the request was rejected. No hidden state changes.
- **Audit on rejection**: emit `autofix.trigger_rejected` with `after={runbook_id, reason:"dry_run_required_for_risky", principal}` — a canary for stale-cache bugs (an unexpected volume here means the UI Real-lockout isn't reaching users).
- **Trade-off**: slightly rougher UX when a user's frontend is stale and doesn't know a runbook was just marked risky (they see a toast error and must re-select dry-run). Acceptable — risky-marked state is meant to be sticky/rare; an error message is more educational than a silent route.

#### Decision C — Audit `initiated_by` shape

**Chosen:** NEW column `initiated_by TEXT NOT NULL DEFAULT 'alert'` on `runbook_runs` via migration 0049. Audit-only (C2) was rejected.

- **Rationale**: STAGE-009-011 (history UI, the immediate downstream consumer) needs to filter/display initiator. Column-first is one migration now vs every future query JOINing `audit_log` and reconstructing which event corresponds to which run — expensive, brittle, and adds hidden coupling between the runs table and audit event names. `initiated_by` is a structural property of a run (like `mode`, `alert_id`, `fixer_user`), not an audit-only side effect.
- **Migration 0049**: `ALTER TABLE runbook_runs ADD COLUMN initiated_by TEXT NOT NULL DEFAULT 'alert'` (backfills historical rows to `'alert'` — correct since no operator trigger existed prior). Values enforced by the enum at the Python layer: `'alert' | 'operator'`.
- **`insert_started` signature widening**: add explicit `initiated_by: Literal['alert', 'operator']` param (NO default — force call sites to be explicit). `handle_alert` path passes `'alert'`; `handle_operator_trigger` path passes `'operator'`.
- **Belt-and-suspenders**: `initiated_by` ALSO recorded in the `autofix.ran` and `autofix.dry_run_stored` audit `after_json`, so audit alone can reconstruct if the runs table ever drifts.
- **Trade-off**: every `insert_started` call site must pass `initiated_by`; one column-write per run added. Small cost for a load-bearing display + filter column.

#### Cross-cutting concerns identified during Design (regression items)

1. **Concurrent operator + alert trigger race** — both paths can enter `_claim_and_exec` for the same runbook simultaneously. Existing per-runbook asyncio.Lock serializes; the in-lock re-gate must use the correct `require_auto_trigger` flag for whichever path claimed second. Regression test: two concurrent triggers (one operator, one alert) — one wins, one gets a cooldown/rate-limit rejection cleanly. (Add to regression.md at Refinement.)
2. **Shared rate-limit bucket** — operator + alert share the same per-runbook rate-limit; an operator hammering "Run fix" could exhaust the budget and starve a real alert-triggered fix. For 010A, keep shared bucket (documented property); revisit in a later stage if it becomes a real problem. Regression item filed.
3. **`alert_id` NULL implications for audit queries** — any existing audit query joining `runbook_runs` on `alert_id IS NOT NULL` (e.g., "runs per alert") will now silently exclude operator runs. Grep audit-consuming code during Build; document any impacted queries in the changelog.
4. **`homelab-fixer` OS user reuse** (non-negotiable #3) — operator trigger still execs as `homelab-fixer`, NOT the operator's principal. Principal is for AUDIT ONLY; exec identity is unchanged. Explicit test at Build.
5. **STAGE-009-011 direct consumer** — `initiated_by` column is a first-class schema contract; when STAGE-009-011 (history UI) is designed, its filter surface should USE this column directly (not synthesize it from audit). File as a design note on STAGE-009-011.
6. **Principal audit for dry-run stored** — operator-initiated dry runs MUST log `who=<principal>` in the `autofix.dry_run_stored` audit (not `who=system:autofix`). Verify both audit sites at Build.
7. **Frontend cache invalidation on trigger** — after a successful operator trigger, the UI needs to invalidate `runbooksKeys.all` AND `approvalsKeys.pending` (for dry-run stored outcomes); on real-run outcomes, also invalidate any future stats query STAGE-009-011 adds. Documented in the new `useTriggerRunbook` hook.
