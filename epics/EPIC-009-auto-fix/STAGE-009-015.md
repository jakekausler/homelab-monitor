# STAGE-009-015: fixer-runner egress enforcement (HTTPS proxy + host firewall)

## Status: Complete

## Overview

Enforce the egress dimension of non-negotiable #2 at network layer. STAGE-009-008 landed egress DECLARATION + a `autofix.egress_unenforced` warning audit on every real exec; enforcement is this stage's job. Add an HTTPS proxy sidecar on the `fixer-egress` docker network + host-side iptables/nftables rules that DROP outbound from the `fixer-runner` container's network namespace except through the proxy. The proxy enforces the runbook's declared `egress` allow-list (captured in 008's `autofix.grant_resolved` audit). The Anthropic API is always in the proxy's allow-list (baseline); runbook-declared endpoints are added per exec.

**Vertical slice:** after this stage, a real exec of a runbook declaring `egress: ["api.anthropic.com"]` can reach ONLY Anthropic; an attempt to reach an undeclared endpoint (curl, DNS, TCP connect) DROPS at the host firewall or is rejected by the proxy. The `autofix.egress_unenforced` warning audit stops firing (or transitions to `autofix.egress_enforced` informational).

**Spec references:** §7.4 (network posture: egress allowed for Anthropic; inbound denied), §7.5 (private docker network `homelab-monitor-net`; `fixer-egress` as separate network in EPIC-009). EPIC-009 LOCKED Decision 2 (egress allow-list per runbook).

## Concrete deliverables

### 1. HTTPS proxy sidecar

New compose service (profile `fixer`) — an egress proxy container (envoy or squid, decided in Design) on the `fixer-egress` network. Proxy config generated per-exec (or dynamic): baseline allow-list = Anthropic API + `install.claude.ai` (for auto-update, if enabled) + DNS. Runbook-declared endpoints added atop the baseline.

### 2. Host firewall rules

`scripts/host-setup.sh` gets a new section (or a new companion script) that installs iptables/nftables rules on the docker host: DROP all outbound from `fixer-runner`'s container netns except to the proxy's IP:port. Idempotent (`--check` verifies without mutation). Uninstall path (`--uninstall` or similar) that restores baseline.

### 3. Orchestrator: proxy config generation per exec

New helper `_configure_egress_for_exec(envelope: _ResolvedGrants) -> None` — writes proxy config (or updates dynamic-reload endpoint) with the union of baseline + `envelope.egress`. Called from `_exec_claude` after `_resolve_grants` succeeds, before `exec_capture`. Failure to configure = fail-closed (`autofix.egress_configuration_error` audit, run errored).

### 4. Audit: transition from `autofix.egress_unenforced` to `autofix.egress_enforced`

STAGE-009-008 emits `autofix.egress_unenforced`. This stage: STOP emitting `unenforced`; START emitting `autofix.egress_enforced` per real exec (informational, not warning). Migration note in changelog.

### 5. Tests

- Baseline exec (no runbook egress declared) → Anthropic reachable, non-Anthropic hosts unreachable (integration test using a disposable test container or the fake claude).
- Runbook-declared endpoint → reachable during exec, unreachable after exec completes (proxy config rolled back).
- Off-list endpoint → connection refused/dropped.
- Kill switch during exec → still kills fixer-runner despite proxy/firewall.
- Idempotent host-setup: `--check` twice is no-op; install twice is no-op.

## Design Phase

**Status**: [x] Design Complete (autonomous loop; brainstormer Opus consulted, coordinator selected)

**Design decisions** (all seven decisions the card flagged for Design, with rationale):

### A — Proxy technology: **Squid 6** (image `ubuntu/squid:6.6-24.04_beta`)

Squid over Envoy. Legibility, ops familiarity, ~60MB image (vs Envoy ~180MB), `squid -k reconfigure` well-tested for hot allow-list reload. Envoy's power (xDS, mTLS, sophisticated routing) is unused for hostname-in-a-list allow-listing. Squid's per-request `access.log` line for CONNECT denials parses trivially for the audit event.

CONNECT allow-list-by-hostname via `acl allowed_hosts dstdomain "/etc/squid/allowlist.txt"` + `http_access allow CONNECT allowed_hosts` + `http_access deny all`. Squid does the DNS resolution — fixer-runner reaches only Squid; no direct DNS reach needed.

Build note: smoke-test `docker exec homelab-fixer-egress-proxy squid -k reconfigure` early — the `ubuntu/squid` Docker Hub description does not explicitly confirm reconfigure support, though the upstream binary supports it universally.

### B — Config generation strategy: **Per-exec file write + `squid -k reconfigure`**

Orchestrator writes `/data/proxy/allowlist.txt` (mounted RW into monitor + RO into proxy) atomically via tmpfile + `os.replace`. Then `docker exec homelab-fixer-egress-proxy squid -k reconfigure`. Wait up to 2s for reconfigure to return; fail-closed on error (see F).

Rejected the dynamic-control-API alternative (Squid external ACL helper) — adds a second process with unclear crash semantics; the state-as-file model is auditable, git-diffable, and debuggable. Reconfigure overhead ~200ms fits comfortably in `_transcript_lock`'s per-exec budget.

### C — Firewall backend: **nftables in a separate table**

nftables over iptables. Docker aggressively rewrites the `FORWARD` chain on restart; iptables rules injected at position 1 get pushed down over time. A separate nftables table (`homelab_fixer`) with an explicit hook priority avoids Docker's rule manipulation entirely. Ubuntu 22.04+ ships nftables natively (verified: `nft --version` = 1.0.2).

Rule shape:
```
table inet homelab_fixer {
  chain forward {
    type filter hook forward priority filter - 10; policy accept;
    iifname "hm-fixegress" oifname != "hm-fixegress" counter drop
  }
}
```

Priority `-10` runs BEFORE Docker's default-priority rules; the `drop` catches any packet leaving the fixer-egress bridge toward the wider host. The proxy sidecar is on the SAME bridge, so proxy → world flows go via the proxy's second network attachment (not via the fixer-egress bridge) — see Docker compose changes below.

**Rejected the `internal: true` docker-network overlay.** The brainstormer recommended it as bonus defense-in-depth: making `fixer-egress` internal and putting the proxy on TWO networks (a second `fixer-uplink` for its outbound). The nftables enforcement is already the hard boundary; the extra network + `internal:` flag doubles the compose surface for near-zero marginal safety benefit. YAGNI: adopt if a future incident motivates it.

### D — Netns identification: **Explicit bridge name via `driver_opts`**

Static-IP-based rules (Option D1) work but couple firewall to Docker's ipam assignments. Explicit bridge name is more robust:

```yaml
networks:
  fixer-egress:
    driver: bridge
    driver_opts:
      com.docker.network.bridge.name: hm-fixegress
    name: ${HM_INSTANCE:-homelab-monitor}-fixer-egress
```

nftables rule matches by `iifname "hm-fixegress"` — catches ALL traffic from the fixer-egress bridge regardless of source container IP. Rejected veth-pair lookup (fragile across restarts) and cgroup match (requires cgroup v2 + docker-specific cgroup path).

### E — host-setup.sh integration: **Extend host-setup.sh with a new §3.10**

New section `§3.10 fixer-egress firewall`, added between §3.9 (fixer-transcript ACL) and the final env-file block (~line 675). Unconditional: no new `--install-egress` flag. host-setup.sh is already run once per host deploy; the firewall rules are harmless before the `hm-fixegress` bridge exists (they only match traffic FROM that bridge). Rules installed to `/etc/nftables.d/homelab-fixer.nft`; loader `systemctl reload nftables`.

`--check` mode extends via the existing `do_or_check` helper (script L118-L125): verify `/etc/nftables.d/homelab-fixer.nft` exists AND `nft list table inet homelab_fixer` succeeds AND the drop rule is present. Idempotent by overwrite-and-reload.

Uninstall path: documented inline as a well-commented `rm /etc/nftables.d/homelab-fixer.nft && systemctl reload nftables` — no `--uninstall` flag (YAGNI; not a load-bearing flag surface today).

### F — Fail-closed retry semantics: **Immediate fail-closed, NO retry**

On `_configure_egress_for_exec` failure (file-write fails OR `docker exec squid -k reconfigure` returns nonzero OR times out at 2s):
1. Emit `autofix.egress_configuration_error` audit with `{runbook_id, alert_id, run_id, error_class, error_message}`.
2. Return `ExecOutcome(errored=True, ...)` — DO NOT call `_docker.exec_capture`.
3. `_current_run` is NOT published, so kill switch has nothing to kill (fine — no fixer exec started).

No retry. `_transcript_lock` guarantees single-flight; there's no proxy-config concurrency race to absorb. Retries hide real proxy issues that ops should see as `autofix.egress_configuration_error` audit events. Total blast radius of a broken proxy: one skipped autofix run per broken state.

### G — Baseline allow-list: **Full Anthropic family**

```
api.anthropic.com
statsig.anthropic.com
install.claude.ai
console.anthropic.com
```

Broader than "just api.anthropic.com" because Claude Code phones home to `statsig.anthropic.com` (feature flags) and `install.claude.ai` (updater). Denying them would produce inconsistent claude behavior vs interactive terminal runs — surprising and hard to diagnose. Trust delta is nil: user already trusts Anthropic with API-key and prompt content.

Fixer-runner env: `HTTPS_PROXY=http://homelab-fixer-egress-proxy:3128` + `NO_PROXY=""` (empty — force all HTTP/HTTPS through Squid). Squid does DNS resolution itself; fixer-runner gets no direct outbound DNS reach (nftables `drop` catches DNS attempts).

Baseline is NOT added to the runbook's declared `egress` grant — it's the Claude-CLI substrate, orthogonal to non-negotiable #2's per-runbook allow-list. `autofix.grant_resolved` payload retains the runbook-declared list unchanged.

**Refinement notes** (validated on instance A, 2026-07-04):

- **Deploy sequence**: rebuilt monitor image with STAGE-009-015 code, recreated `homelab-monitor-fixer-egress` network with `driver_opts.com.docker.network.bridge.name: hm-fixegress`, brought up new `fixer-egress-proxy` service, host-setup.sh installed `/etc/nftables.d/homelab-fixer.nft` (contents match spec; `nft -f`-loaded via `systemctl reload nftables`).
- **Squid log destination fix** (real-deploy issue caught in Refinement): initial `squid.conf` used `access_log stdio:/dev/stdout` + `cache_log stdio:/dev/stderr`, which crashed under the `ubuntu/squid` image's default `cache_effective_user proxy` (uid can't write to root-owned stdio). Fixed to `access_log /var/log/squid/access.log squid` + `cache_log /var/log/squid/cache.log` — Squid-writable paths inside the image.
- **`fixer-uplink` network added** (real-deploy issue caught in Refinement): initial design put the proxy on `fixer-egress` only. That worked fine at the ACL layer (Squid correctly denied/allowed CONNECT), but the proxy's OWN outbound went via the `hm-fixegress` bridge — and the nftables rule dropped it, so Squid's `TCP_TUNNEL` hung 60s → 503 on every allowed target. Fix: added a second bridge network `fixer-uplink` (not attached to fixer-runner) and put the proxy on BOTH networks with `gw_priority: 100` on `fixer-uplink` to force it as the default gateway. Proxy's outbound now leaves via fixer-uplink (not hm-fixegress), so the nftables rule is unaffected. Design brainstormer recommended this defense-in-depth layer in Design; the coordinator rejected it as YAGNI at the time. Refinement proved it's load-bearing (the proxy needs an uplink that isn't the enforcement bridge).
- **Inode-preserving write** (real-deploy issue caught in Refinement): the orchestrator originally used `tempfile.mkstemp` + `os.replace` for the allowlist.txt write — atomic on POSIX, but the resulting inode-swap breaks the container's bind mount (Squid inside the container sees the OLD inode → stale allow-list). Fix: replaced with `open(allowlist_path, "w")` truncate-in-place. Not POSIX-atomic, but safe because `_transcript_lock` guarantees single-flight and Squid's reconfigure isn't called until after the write completes. Removed `tempfile` + `contextlib.suppress` imports + deleted three atomic-write tests (see Build notes deltas below).
- **`priority:` vs `gw_priority:` compose syntax** (real-deploy issue caught in Refinement): the coordinator first tried `priority: 100` on the network attachment. Docker Compose v2.35.1 silently ignored it (`priority` is for connection order, not gateway selection). Correct field for Docker Compose 2.32+ is `gw_priority`. Fixed.
