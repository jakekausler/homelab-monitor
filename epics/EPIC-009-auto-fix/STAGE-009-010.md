## Design Phase

### Approach

Build the `/runbooks` route as a native TanStack Router page (top-level, not nested under `/settings` — Runbooks are a first-class surface). The page has two stacked sections: (A) **Runbooks catalog** — one card per registered runbook, and (B) **Pending approvals** — a review-and-act surface for dry-run plans awaiting operator decision. STAGE-009-010 DEFERS the manual "Run fix" trigger to a new tracked stage (STAGE-009-010A) because the backend trigger endpoint does not exist and its safety design (operator allow-list semantics, audit shape, orchestrator entry point) is non-trivial. The stage owns the approval-review UI because non-negotiable #5 (risky runs require plan + explicit approval) leaves a safety-critical gap otherwise — risky alerts fire real, produce pending approvals, and today there is no UI to act on them.

### Selected decisions (autonomous — this loop is autonomous)

**Decision 1 — Manual-trigger endpoint: DEFER to STAGE-009-010A (BACKEND + small FRONTEND).** New stage owns the operator-initiated trigger endpoint (`POST /api/runbooks/{id}/trigger` or equivalent), the allow-list semantics for operator-initiated runs, the `initiated_by=operator` audit convention, and the UI Run-fix button + trigger modal on 010's catalog cards. Also bundles the defense-in-depth backend rejection of `PATCH auto_trigger=true` on `risky` runbooks (today's backend does NOT reject this; the safety net is exec-time only via `dry_run_required`).

**Decision 2 — Last-run + success-rate on catalog cards: DEFER to STAGE-009-011.** 011 already owns `runbook_runs` data and the transcript viewer. 011's card MUST be extended with an explicit deliverable: expose an aggregation endpoint (`GET /api/runbooks/stats` or extend `GET /api/runbooks` with joined fields) that feeds BOTH the history table AND the 010 catalog card summary (last_run_at, last_run_status, success_rate_30d, run_count_30d). 010 renders em-dash placeholders with an info-icon tooltip "Coming in Auto-fix history" (links to `/settings/logs` for now, retargeted to `/autofix-history` when 011 lands).

**Decision 3 — Approval-review UI: 010 OWNS FULL APPROVAL-REVIEW.** Non-negotiable #5 mandates a review surface for pending dry-run plans. 010 ships a "Pending approvals" `<Card>` section below the catalog grid, using `GET /api/autofix/approvals?status_filter=pending`. Row click opens a Radix `Dialog` showing `plan_text` (scrollable `<pre>` — no size cap; the plan endpoint returns the full transcript verbatim), an Approve button (opens `ConfirmPhraseDialog` with expectedPhrase `"approve"`, calls `POST /api/autofix/approvals/{id}/approve`), and a Reject button (calls `POST /api/autofix/approvals/{id}/reject`). Surfaces `drift_detected` per row (server-computed) as an amber badge and blocks Approve if drift is detected. Renders 409-error `code` strings clearly: `runbook_changed_since_plan`, `runbook_missing`, `kill_switch`, `allow_list`, `rate_limit`, `cooldown`, `already_running`, `approval_not_pending`. NOTE: STAGE-009-011 still owns the general-purpose transcript viewer across ALL runs (both dry and real, not gated to approvals).

**Decision 4 — Confirm-on-destructive mechanism: TYPED-PHRASE only (reuse `ConfirmPhraseDialog`).** Consistent with STAGE-009-006 (approve) and STAGE-009-007 (kill-switch). File a new STAGE-009-010B for session-PIN confirm-on-destructive with owner-explicit acceptance criteria (per the no-silent-deferral discipline).

**Decision 5 — Manual-trigger UI location: MOOT for 010 (Decision 1 defers).** For STAGE-009-010A (informing 010's card layout): modal from a per-card "Run fix" button (reuses Radix Dialog + `ConfirmPhraseDialog`). 010's cards do NOT ship a disabled placeholder button — cleaner to add the button when 010A lands.

### Additional design details

- **Route**: New TanStack route `/runbooks` (top-level). Component `RunbooksPage` in `apps/ui/src/routes/runbooks/RunbooksPage.tsx`. Replace `SidebarNav.tsx:50` placeholder with `{ label: 'Runbooks', to: '/runbooks', icon: FileText }`. The "Auto-fix history" placeholder at line 51 stays until STAGE-009-011.
- **API hook file**: `apps/ui/src/api/runbooks.ts`. Hooks: `useRunbooks()`, `useToggleRunbook()`, `useRefreshRunbooks()`, `usePendingApprovals()`, `useApprovalPlan(approvalId)`, `useApproveApproval()`, `useRejectApproval()`. Query keys: `runbooksKeys.all = ['runbooks'] as const`; `approvalsKeys.pending = ['autofix-approvals', 'pending'] as const`; `approvalsKeys.plan = (id: string) => ['autofix-approvals', 'plan', id] as const`. CSRF automatic via `apiClient` middleware.
- **Kill-switch integration**: reuse `useAutofixKillSwitch()` from `apps/ui/src/api/autofixSettings.ts`. When `enabled === false`: (a) render an amber banner at page top linking to `/settings/autofix`; (b) disable Enabled and Auto-trigger toggles on all cards with tooltip "Auto-fix disabled — enable in Settings"; (c) disable Approve buttons on pending approvals with the same tooltip (backend will 409 with `kill_switch` otherwise).
- **Auto-trigger toggle on risky runbooks**: LIVE toggle (not locked). Rationale: setting `auto_trigger=true` on a risky runbook does not auto-execute — it auto-produces a pending approval when a matching alert fires. That is a legitimate, useful workflow (auto-produce plans for review). An info icon on risky cards explains: "Auto-trigger produces a pending approval on match (not a real run). Approve to execute." Backend defense-in-depth to reject this PATCH is DEFERRED to STAGE-009-010A (per Decision 1's bundle).
- **Card contents (per runbook)**: (1) Title = `basename(path)` (the folder name — no `name` field exists on Runbook); (2) Risk badge (green "safe" / amber "risky"); (3) `dry_run_required` sub-badge (only if true); (4) Alert match patterns rendered as compact chips (up to 3, "+N more" suffix if longer, hover to reveal all); (5) Rate-limit + cooldown summary line if either set; (6) Two Radix Switch toggles: Enabled + Auto-trigger; (7) Stats row: "Last run: —" / "Success rate: —" with info-icon tooltip "Coming in Auto-fix history"; (8) Footer: "Config folder" label with `path` as inline code + copy button.
- **Refresh button**: page header contains a "Refresh from disk" button calling `POST /api/runbooks/refresh`. Success toast: "Registered X, refreshed Y, skipped Z (W errors)". Errors listed in a collapsible detail if any.
- **Empty state**: use `EmptyState` component when 0 runbooks: body "No runbooks registered. Add a `runbook.yaml` under `runbooks/<name>/` on disk, then click Refresh."
- **Grid**: `grid grid-cols-1 gap-4 md:grid-cols-2 xl:grid-cols-3` (Overview.tsx pattern).
- **Pending approvals panel**: `<Card>` below the catalog. `CardTitle="Pending approvals"`. Empty: "No pending approvals." Populated: rows with runbook_id, created_at (relative), drift-detected amber badge if set, "View & Approve" button opening the plan Dialog.
- **Plan Dialog**: shows `plan_text` in a scrollable `<pre>` (max-h with overflow-auto), copy-to-clipboard button, Approve + Reject buttons at footer. Approve fires ConfirmPhraseDialog. Reject fires with no phrase (Reject is non-destructive per safety model — the risky run does not execute).
- **Mobile viewport**: cards stack 1-col at <768px (grid default). Approvals rows stack vertically (test verifies).
- **Data flow verified against real backend**: `GET /api/runbooks` returns `RunbookOut` with fields (`id`, `path`, `created_at`, `alert_match_patterns`, `risk_tag`, `dry_run_required`, `rate_limit_per_hour`, `cooldown_seconds`, `enabled`, `auto_trigger`, `content_hash`) — NO `name`, NO `last_run`, NO `success_rate`. `PATCH /api/runbooks/{id}` accepts `{enabled?, auto_trigger?}`. `GET /api/autofix/approvals?status_filter=pending` returns per-row `drift_detected` (server-computed). `GET /api/autofix/approvals/{id}/plan` returns full transcript verbatim as `plan_text` (no size cap — will show large strings; scrollable `<pre>` handles this). `POST /api/autofix/approvals/{id}/approve` requires exact typed phrase `"approve"` (no strip, no case-fold). `POST /api/autofix/approvals/{id}/reject` empty body.

### Options presented

**UI Options Presented:** brainstormer (Opus) explored 3 options each for five cross-cutting decisions (manual-trigger endpoint scope; last-run/success-rate data source; approval-review ownership; confirm-on-destructive mechanism; manual-trigger UI location). All five recommendations were adopted, with one refinement: risky-runbook auto-trigger toggle remains LIVE (not locked) — the risky safety net is exec-time (dry_run_required routes to approval), and auto-producing a pending approval on a risky match is a legitimate workflow. Backend defense-in-depth rejection of that PATCH is deferred to STAGE-009-010A per the Decision 1 bundle. Plan-viewer scope in the approval Dialog is minimal (scrollable `<pre>` + copy) — 011 owns the general transcript viewer for all runs.

**User Choice:** Selected by the implementing session (autonomous epic-loop). Rationale: (Decision 1) defer manual-trigger keeps 010 focused on the frontend surface and forces honest backend design for operator-initiated allow-list in its own stage per non-negotiable #1; (Decision 2) defer stats to 011 respects domain ownership — 011 owns runs data end-to-end; (Decision 3) 010 owning approval-review is required by non-negotiable #5 — deferring leaves risky runs from real alerts with no review surface; (Decision 4) typed-phrase reuses proven pattern from 006/007 and keeps 010 lean while filing session-PIN as its own stage per no-silent-deferral; (Decision 5) modal-per-card location is best UX for a one-shot trigger and defers cleanly to 010A.

### Refinement notes

Viewport sign-off performed against the prod stack (`make dev-prod` → http://127.0.0.1:29090) using a stub runbook `/storage/programs/homelab-monitor/runbooks/stage010-refinement-stub/` (deleted after approval). Two iterations of fixes were required before both viewports approved:

**Fix 1 — Sidebar not scrollable on mobile.** The shared `SidebarNav` component's root `<nav>` element had `h-full` but no `overflow-y-auto`, causing nav items to clip at the bottom of tall lists (both mobile and any narrow-viewport desktop). Added `overflow-y-auto` to `apps/ui/src/components/SidebarNav.tsx` line 82. The reported "Runbooks disabled on mobile" turned out to be a stale bundle in the user's browser (the shared component was already correctly wired — no separate mobile nav list exists) — resolved by hard-reload after the rebuild.

**Fix 2 — Backend refresh error: "runbooks root /runbooks is not a directory".** Root cause: `deploy/compose/docker-compose.yml` was missing a bind-mount for `/runbooks` (the backend defaults `HOMELAB_MONITOR_RUNBOOKS_DIR` to `/runbooks` per STAGE-009-004, but no compose mount was ever added). Added `${HM_RUNBOOKS_SRC:-../../runbooks}:/runbooks:ro` to the monitor service's volumes list. STAGE-009-010's UI surfaced this pre-existing STAGE-009-004 infrastructure gap because it was the first user-facing consumer of the runbooks endpoint.
