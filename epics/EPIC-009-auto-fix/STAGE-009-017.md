# STAGE-009-017: Registry row pruning on `POST /api/runbooks/refresh`

## Status: Complete — 2026-07-04

## Overview

Fix the STAGE-009-004 back-patch gap: `POST /api/runbooks/refresh` currently reconciles NEW folders into the `runbooks` DB table but does NOT prune rows whose folders have been deleted from disk. This leaves stale registry entries listed by `GET /api/runbooks` after a user removes a runbook folder.

**Deferred from:** STAGE-009-012 Design (2026-07-03). Origin regression item filed under STAGE-009-010 Refinement (2026-07-02). Audit implication is small: `runbook_runs.runbook_id` references are historical snapshots and are NOT FK-enforced against the registry, so pruning a registry row does not orphan history — but the pruning IS audit-relevant (emit `autofix.runbook_registry_pruned` audit row).

## Stage Flags

- Has Input Forms: [ ] No
- Touches secrets / production data: [ ] No — only registry lifecycle.
- Host-integration concerns: [ ] No

## Concrete deliverables

1. Extend `RunbookRepo.reconcile` (or the refresh handler) to detect registry rows whose `path` no longer exists on disk after a scan; DELETE those rows; emit `autofix.runbook_registry_pruned` audit_log rows.
2. Preserve historical `runbook_runs.runbook_id` references (they are not FK-enforced to the registry; pruning is safe).
3. Regression test: create runbook folder → refresh → confirm listed; delete folder → refresh again → confirm not listed + audit row emitted.

## Design Phase

**Status**: [x] Design (Complete) — 2026-07-04

### Design Notes (2026-07-04) — Approach A1+B2+C1+D1(+D-skip)+E2, no migration

**Autonomous selection** by the implementing session (epic-stage loop). Recorded per the loop's authoritative directive that Design decisions are made and recorded by the coordinator, not user-prompted.

**Key verified facts (contradict earlier assumption):**
- `runbook_runs.runbook_id` **IS** FK-enforced against `runbooks.id` (alembic/versions/0001_initial_schema.py:154–159, `nullable=False`, no `ondelete` — SQLite default RESTRICT). The handoff and the STAGE-009-010 Refinement note both stated this FK was absent; the verified code says otherwise. This changes the design.
- `runbook_run_approvals.runbook_id` and `alerts.runbook_id` are plain `sa.Text()` with no FK — dangling refs safe: no SQL JOINs, existing runtime `RUNBOOK_MISSING` handling in `orchestrator.py:1377–1414` already surfaces "runbook was deleted after plan captured" as 409. `alerts.runbook_id` is dead-lettered (never written to by any code path).
- Existing audit event naming convention in `repository.py` is bare snake_case (`runbook_registered`, `runbook_refreshed`, `runbook_gates_changed`) — NOT dotted. The handoff's suggested `autofix.runbook_registry_pruned` would break local convention.

**Selected approach:**

- **Axis A — Delete strategy: A1** — Hard-DELETE only if `SELECT COUNT(*) FROM runbook_runs WHERE runbook_id = :id` returns 0. If runs history exists, keep the row + emit a `runbook_prune_skipped` audit. Rationale: no migration, FK is a natural guard, both current prod orphans have `enabled=0 auto_trigger=0` and were pre-execution refinement stubs (almost certainly zero runs).
- **Axis B — Transaction structure: B2** — Per-prune transaction (one `DELETE FROM runbooks WHERE id = ?` + one `insert_audit(...)` per row), mirrors the existing `_insert`/`_update_cached` idiom.
- **Axis C — Prune eligibility: C1** — Prune only when `not Path(row.path).exists()`. Loader errors (folder present, invalid content) keep the row so operator can fix the file. Loader errors continue to surface via existing `errors: list[LoadError]` field.
- **Axis D — Audit event & payload:**
  - `runbook_pruned`: `before={id, path, content_hash, enabled, auto_trigger, risk_tag}`, `after=None`, `who=principal_label(who_principal)`, `ip=<request_ip>`.
  - `runbook_prune_skipped` (companion for A1's history-blocked rows): `before={id, path, runs_count}`, `after=None`, same `who`/`ip`.
  - Matches local naming convention; NOT dotted. Full-snapshot `before` payload preserves forensic state without joining backward.
- **Axis E — HTTP response extension: E2** — Add `pruned: list[str] = Field(default_factory=list)` AND `prune_skipped: list[str] = Field(default_factory=list)` to both `RefreshResponse` (Pydantic) and `RefreshOutcome` (dataclass). Pydantic defaults keep existing tests passing without modification.
- **Axis F — UI: no change** — pruned rows disappear naturally from `GET /api/runbooks`; audit_log is the trail. STAGE-009-004 registry list surface unchanged. If operators later want a "N rows pruned" indicator, it becomes a follow-up.

**Non-negotiable compliance:**
- **#4 Audit:** Both prune and prune-skip emit `insert_audit` inside the same txn as the `DELETE`. Both material state changes AND the explicit-non-change (couldn't prune due to history) are audited.
- **#7 Kill switch:** unaffected — prune doesn't invoke Claude, doesn't affect the global auto-fix disable state.
- **#1 Trigger / #2 Scope / #3 Identity / #5 Dry-run / #6 Rate limit:** irrelevant — this is a registry-lifecycle DB operation, no runbook execution.

**Files to modify (Build):**
- `apps/monitor/homelab_monitor/kernel/runbooks/repository.py` — extend `reconcile()`, add `_prune()` method mirroring `_insert`/`_update_cached`, add `_prune_skipped_audit()` helper, add prune SQL constants. Extend `RefreshOutcome` dataclass with `pruned` + `prune_skipped` (defaulted).
- `apps/monitor/homelab_monitor/kernel/api/routers/runbooks.py` — extend `RefreshResponse` with `pruned` + `prune_skipped` (Field default_factory list), pipe through `refresh_runbooks` handler.
- `apps/monitor/tests/test_runbooks_repo.py` — 4 new tests: prune-happy, prune-blocked-by-history, folder-exists-but-loader-error-not-pruned, mixed-batch.
- `apps/monitor/tests/test_api_runbooks.py` — 1 new HTTP test surfacing `pruned` in response.
- No migration.
- No UI changes.

**Regression test scenario (per stage card deliverable 3):**
Repo-level integration test: create folder → reconcile (registered) → delete folder → reconcile again → assert `pruned == [folder_path]`, row absent from DB, `runbook_pruned` audit row present.

**Prod Refinement candidates:** 2 natural orphan rows already in prod DB (`stage010-refinement-stub`, `stage016-refinement-test`) — both `enabled=0 auto_trigger=0`, folders missing from disk. Refinement will trigger `POST /api/runbooks/refresh` and verify both are pruned (assuming zero runs history — verify before running with `SELECT COUNT(*) FROM runbook_runs WHERE runbook_id IN (...)`); if either has runs, it should surface as `prune_skipped` with an audit row.

**Deferred / open questions (all non-blocking, tracked here):**
1. Pending `runbook_run_approvals` for a pruned runbook_id will remain in the pending-approvals list forever (existing runtime code returns 409 on approve; reject works). Cleaning them up proactively is a scope expansion — deferred. If it proves painful in practice, a follow-up stage would extend prune to also transition pending approvals to `rejected` with the existing `RUNBOOK_MISSING` audit shape (`orchestrator.py:1382–1405`).
2. `alerts.runbook_id` cleanup: no-op — column is dead-lettered in current code (never populated).
3. Adding an `ondelete=RESTRICT` (explicit) or CASCADE to the `runbook_runs.runbook_id` FK is a future infra tightening — not needed here since SQLite default matches our intent.
