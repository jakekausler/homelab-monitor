# STAGE-009-010B: Auto-fix UI — session-PIN confirm-on-destructive (replaces typed-phrase across destructive actions)

## Status: Not Started

## Overview

Replaces the typed-phrase confirm-on-destructive UX (used today in STAGE-009-006 approve, STAGE-009-007 kill-switch, and STAGE-009-010A manual real-run) with a session-PIN mechanism. The user sets a PIN at first use (or on-demand); destructive actions require entering the PIN instead of retyping a phrase. Optional: per-action PIN vs session-wide PIN with a short TTL after entry.

**Vertical slice:** after this stage, all destructive actions in the auto-fix UI use the same PIN mechanism; the typed-phrase paths remain as a fallback if no PIN is set.

**Origin:** deferred from STAGE-009-006 (regression note: "session-PIN confirm-on-destructive → deferred to 010/011") and re-affirmed as a distinct owned stage during STAGE-009-010 Design 2026-07-02.

**Spec references:** §7.4 non-negotiable #5 (dry-run approval); §7.2 (confirm-on-destructive).

## Cross-cutting standards

- Backend must rate-limit PIN attempts (guard against brute force). Failure lockout with progressive backoff.
- PIN stored hashed (bcrypt with existing HM_MONITOR_BCRYPT_COST); never plaintext, never logged.
- PIN reset requires re-authentication (session cookie proof); session PIN entry has a short TTL (e.g., 5 min).
- All destructive-action endpoints accept EITHER the typed phrase OR the PIN during transition; a follow-up stage may drop the phrase path.
- Frontend stage → Desktop + Mobile viewport sign-off.

## Concrete deliverables

### 1. Backend PIN endpoints

`POST /api/settings/security/pin` set/update PIN (requires session cookie + confirm-on-destructive typed phrase for setting/rotating).
`POST /api/settings/security/pin/verify` verify PIN (short-TTL session flag).
`DELETE /api/settings/security/pin` remove PIN.
Rate-limit + progressive backoff on `/verify`.

### 2. Destructive-action endpoints accept PIN OR phrase

`POST /api/settings/autofix/kill-switch` (STAGE-009-007), `POST /api/autofix/approvals/{id}/approve` (STAGE-009-006), and STAGE-009-010A's manual-trigger endpoint accept either `{confirm_phrase}` or `{confirm_pin}` in the body.

### 3. Frontend PIN management surface

Settings page for PIN set/rotate/delete. `ConfirmPinDialog` reusable component (mirrors `ConfirmPhraseDialog` UX).

### 4. Frontend destructive-action integration

Kill-switch (STAGE-009-007), Approve (STAGE-009-010), and Run-fix real (STAGE-009-010A) use `ConfirmPinDialog` if a PIN is set; fall back to `ConfirmPhraseDialog` if not.

### 5. Tests + sign-off

Backend pytest: PIN CRUD, rate-limit + backoff, hashing, destructive endpoints accept both credentials, wrong PIN denied. Vitest: PIN set/rotate/delete flows; destructive actions use PIN dialog when PIN set; fall-back to phrase when not. Desktop + Mobile viewport sign-off.
