# STAGE-009-010B: Auto-fix UI — session-PIN confirm-on-destructive (replaces typed-phrase across destructive actions)

## Status: Complete

## Overview

Replaces the typed-phrase confirm-on-destructive UX (used today in STAGE-009-006 approve, STAGE-009-007 kill-switch, and STAGE-009-010A manual real-run) with a session-PIN mechanism. The user sets a PIN at first use (or on-demand); destructive actions require entering the PIN instead of retyping a phrase. Optional: per-action PIN vs session-wide PIN with a short TTL after entry.

**Vertical slice:** after this stage, all destructive actions in the auto-fix UI use the same PIN mechanism; the typed-phrase paths remain as a fallback if no PIN is set.

**Origin:** deferred from STAGE-009-006 (regression note: "session-PIN confirm-on-destructive → deferred to 010/011") and re-affirmed as a distinct owned stage during STAGE-009-010 Design 2026-07-02.

**Spec references:** §7.4 non-negotiable #5 (dry-run approval); §7.2 (confirm-on-destructive).

## Stage Flags

- Has Input Forms: [x] Yes — PIN set + PIN entry
- Touches secrets / production data: [x] Yes — the PIN gates destructive auto-fix actions
- Host-integration concerns: [ ] No

## Cross-cutting standards

- Backend must rate-limit PIN attempts (guard against brute force). Failure lockout with progressive backoff.
- PIN stored hashed (bcrypt with existing HM_MONITOR_BCRYPT_COST); never plaintext, never logged.
- PIN reset requires re-authentication (session cookie proof); session PIN entry has a short TTL (e.g., 5 min).
- All destructive-action endpoints accept EITHER the typed phrase OR the PIN during transition; a follow-up stage may drop the phrase path.
- Frontend stage → Desktop + Mobile viewport sign-off.

## Concrete deliverables

### 1. Backend PIN endpoints

`POST /api/settings/security/pin` set/update PIN (requires session cookie + confirm-on-destructive typed phrase for setting/rotating).
`POST /api/settings/security/pin/verify` verify PIN (short-TTL session flag).
`DELETE /api/settings/security/pin` remove PIN.
Rate-limit + progressive backoff on `/verify`.

### 2. Destructive-action endpoints accept PIN OR phrase

`POST /api/settings/autofix/kill-switch` (STAGE-009-007), `POST /api/autofix/approvals/{id}/approve` (STAGE-009-006), and STAGE-009-010A's manual-trigger endpoint accept either `{confirm_phrase}` or `{confirm_pin}` in the body.

### 3. Frontend PIN management surface

Settings page for PIN set/rotate/delete. `ConfirmPinDialog` reusable component (mirrors `ConfirmPhraseDialog` UX).

### 4. Frontend destructive-action integration

Kill-switch (STAGE-009-007), Approve (STAGE-009-010), and Run-fix real (STAGE-009-010A) use `ConfirmPinDialog` if a PIN is set; fall back to `ConfirmPhraseDialog` if not.

### 5. Tests + sign-off

Backend pytest: PIN CRUD, rate-limit + backoff, hashing, destructive endpoints accept both credentials, wrong PIN denied. Vitest: PIN set/rotate/delete flows; destructive actions use PIN dialog when PIN set; fall-back to phrase when not. Desktop + Mobile viewport sign-off.

**Status**: Complete

**Approach chosen**: Selected by the implementing session (autonomous epic-loop; no user prompt this phase). Rationale: brainstormer (Opus) presented 2-3 options for each of the four architecturally non-trivial decisions grounded in real-code discovery of the storage/session/rate-limit/audit/bcrypt infra. Chosen options were the least-infra path that preserves ALL seven auto-fix non-negotiables and matches the LOCKED project-wide "single-user single-admin homelab" reality.

### Decision A — PIN storage location

**Options considered**:
- A1 — `app_settings` row (`security.pin_hash` → bcrypt string; TTL/lockout state elsewhere). Zero migration; matches single-admin reality.
- A2 — New `security_pins` table (per-user, FK to users). Anticipates multi-user; over-engineered today.
- A3 — Extend `users` with nullable `pin_hash` column. Cheapest per-user path but widens the deliberately-narrow `users` table and re-introduces the "`User` model must exclude hash fields" footgun that the `bcrypt_hash` docstring warns about.

**Selected**: **A1 — `app_settings` row (`security.pin_hash`)**.

**Rationale**: Single-admin is a locked project reality (spec §7.4, auth-stage decision D4). A2/A3 both spend migration budget and cognitive complexity to anticipate a multi-user future the spec disclaims. `app_settings` already holds security-adjacent state (`autofix_enabled` kill-switch). Migrating one row to a `security_pins` table if multi-user ships later is a trivial future data-move — cheaper than paying A2/A3 today. Avoids A3's `User`-model leak footgun entirely.

### Decision B — Session-PIN TTL semantics

**Options considered**:
- B1 — Server-side session-wide flag (TTL after successful verify skips PIN re-entry). Requires mutating `sessions` (never done today; model is `frozen=True`) or a sibling `session_pin_verifications` table. Widens attack surface: stolen cookie inside TTL bypasses friction gate.
- B2 — Per-action PIN (no TTL, no state). Every destructive action re-prompts. Simplest infra; friction gate never weakens.
- B3 — Hybrid: server stateless, UI-side TTL cache. Reintroduces a "PIN in JS memory" XSS-widening for TTL window.

**Selected**: **B2 — Per-action PIN (no TTL)**.

**Rationale**: Safety-model treats confirm-on-destructive as a real friction gate (§7.2) with rate-limit + cooldown (§6). Any TTL that authorizes multiple destructive actions from a single credential entry weakens the gate. B2 preserves it cleanly with ZERO new infra: no `sessions` UPDATE (pattern break), no new table, no client cache. Friction cost is bounded — three destructive endpoints are used rarely (approval per-approval, kill-switch is emergency, trigger is manual runbook exec) — handful of PIN entries per week for a single admin. If usage proves intolerable, B3 (client-only TTL) is an easy follow-up with unchanged server contract.

### Decision C — Rate-limit + progressive backoff backend

**Options considered**:
- C1 — In-process `InProcessPinRateLimiter` (sibling to existing `InProcessLoginRateLimiter`). Matches locked D4; zero infra; lost on restart (accepted trade-off already).
- C2 — DB-backed `pin_attempts` table + `pin_locked_until` column. Survives restart; new migration + repo; drifts from login pattern.
- C3 — Extend existing `LoginRateLimiter` bucket for PIN too. Directly weakens safety (login failures lock out PIN attempts and vice versa; changes login backoff behavior).

**Selected**: **C1 — In-process `InProcessPinRateLimiter`, keyed by `user.id`, curve-based backoff**.

**Rationale**: Direct pattern extension of a LOCKED decision (auth-stage D4). C2 pays real cost for restart-survival that the login flow already declined. C3 introduces cross-credential lockout — a real safety regression (bad-actor guessing password locks admin out of runbook approval).

**Concrete curve** (locked here for Build):
- Failures 1-2 in window: no wait.
- Failure 3: retry-after 5 seconds.
- Failure 4: retry-after 30 seconds.
- Failure 5: retry-after 5 minutes (lockout).
- Window: 15 minutes (sliding).
- Reset: successful `/verify` clears the user's deque.
- 429 response includes a `retry_after_seconds: int` field for UI to render backoff. Also sets standard `Retry-After` header.

**Key by `user.id`** (single user → one bucket) rather than IP — PIN is a per-user credential. Login limiter's IP-keying is a login-specific concern.

### Decision D — Endpoint migration path

**Options considered**:
- D1 — Per-endpoint `confirm_pin: str | None` alongside `confirm_phrase: str | None`, each handler branches. Explicit but duplicates safety-critical logic (rate-limit, audit `credential_type`) across three handlers → forget-one-site regression risk.
- D2 — Shared FastAPI `Depends(require_destructive_confirmation)`. Body-reading Depends is awkward with FastAPI when the endpoint has its own Pydantic model; per-endpoint phrase differences (approve exact-eq vs kill-switch case-fold) still need per-call config.
- D3 — Reusable helper function `verify_destructive_credential(body, user, request, *, expected_phrase, phrase_match_mode) -> Literal['pin','phrase']`. All the dedup of D2 without the Depends body-reading awkwardness; explicit at each handler; helper wraps rate-limit + backoff + audit-credential-type dispatch.

**Selected**: **D3 — reusable helper function + server-side phrase added to the trigger endpoint**.

**Rationale**: D3 centralizes the phrase-vs-PIN dispatch, rate-limit call, and backoff (three concerns that MUST be identical across all three endpoints for the safety story to hold), while allowing per-endpoint expected-phrase config as kwargs. Return value `Literal['pin','phrase']` drives audit `after={credential_type: ...}` directly.

**Sub-decision — trigger endpoint gets server-side phrase too**: The trigger endpoint (`POST /runbooks/{id}/trigger`) currently has NO server-side confirmation of any kind — RunFixDialog gates client-side by basename phrase, but a direct-API call bypasses it entirely. 010B is the natural moment to close this asymmetry: trigger accepts EITHER `confirm_pin` OR `confirm_phrase` (basename-derived from the loaded runbook object). Symmetric with approve/kill-switch. Closes a real gap where a scripted call could bypass the UI on the most-destructive endpoint (arbitrary-command exec).

### Decision E — PIN set/rotate/delete authentication ceremony (locked here for Build)

- PIN set/rotate/delete all require a valid session cookie (existing `require_session()` dependency) — CSRF is auto-enforced for POST/DELETE by the middleware.
- PIN set (when no PIN exists): password re-prove required (mirror `POST /api/auth/change-password` precedent — pass `current_password` in the body). Rationale: bootstraps the trust chain — you cannot set a PIN without knowing the password. Prevents session-cookie-only privilege escalation.
- PIN rotate (change existing PIN): both `current_pin` AND `new_pin` required in the body. Wrong `current_pin` → 400 (also ticks the rate-limiter). Rationale: you cannot rotate the PIN with just the PIN cookie — you must actively prove knowledge of the existing PIN. Note: password re-prove is NOT required on rotate — PIN knowledge is sufficient, matching the "PIN is a step-down credential from the password" mental model.
- PIN delete: password re-prove required (same as set). Rationale: removing the PIN weakens future destructive gates — treat as high-trust op.
- All four endpoints (set/verify/rotate/delete) write audit rows: `autofix.pin_set`, `autofix.pin_verified`, `autofix.pin_rotated`, `autofix.pin_removed`. Verify failure emits `autofix.pin_verify_failed`; lockout emits `autofix.pin_locked`.

### Decision F — PIN format + validation (locked here for Build)

- **Length**: 4-12 digits (numeric only). Rationale: a PIN is a fast typed second factor, not a password. Numeric is faster on mobile keyboards (matches Refinement's Desktop+Mobile requirement). Min 4 gives 10K keyspace; combined with the progressive backoff curve (5 attempts → 5min lockout), even worst-case 4-digit PIN has effectively unbrute-forceable throughput.
- **Character class**: `^[0-9]{4,12}$` — Pydantic `Field(pattern=...)`.
- **No complexity rules** beyond length + digits (mirrors the password model — length is the only complexity gate).
- **Storage**: `pin.encode("utf-8")` → `bcrypt.hashpw(..., bcrypt.gensalt(rounds=DEFAULT_BCRYPT_COST))` → decoded UTF-8 string in `security.pin_hash` value column. Mirrors login `hash_password` exactly.

### Decision G — UI surface + component design (locked here for Build)

- **Settings page location**: `apps/ui/src/routes/settings/SettingsSecurityPage.tsx` — new page at `/settings/security` (new route). Section: "Auto-fix confirmation PIN" with Set/Rotate/Delete actions. Shown ONLY when the session user has a password (i.e., always in current single-admin project). Uses existing shadcn Card + form primitives.
- **`ConfirmPinDialog` component location**: `apps/ui/src/components/ConfirmPinDialog.tsx` — sibling of `ConfirmPhraseDialog.tsx`. Same prop shape as `ConfirmPhraseDialog` (`open`, `onOpenChange`, `title`, `body`, `confirmLabel`, `onConfirm(pin: string)`, `isPending`, `errorMessage?`), with two differences:
  - No `expectedPhrase` prop — the PIN is verified server-side by `/verify` (client shows a shape-only 4-12-digit gate for the submit button, no client-side match).
  - `onConfirm` receives the entered PIN string so the caller can send it as `confirm_pin` in the destructive-action body. (`ConfirmPhraseDialog`'s `onConfirm` receives no args because the phrase is trusted client-side; PIN must always cross the wire.)
- **Fallback logic**: three destructive-action call sites (`ApprovalPlanDialog`, `SettingsAutofixPage` kill-switch, `RunFixDialog`) use a new hook `usePinStatus()` that calls `GET /api/settings/security/pin` (existence-check endpoint returning `{ set: bool }`; NOT the PIN value — never leaks the hash). If `pin_set === true`, mount `ConfirmPinDialog` with the caller-appropriate title/body; else mount `ConfirmPhraseDialog` (existing per-endpoint expected phrase logic unchanged).
- **PIN-set page dialog UX**: initial set uses a two-field form (PIN + confirm PIN, both must match client-side + digit-shape gate). Rotate uses three fields (current PIN + new PIN + confirm new PIN). Delete uses one field (password re-prove).
- **Wrong-PIN error surface**: 400 → red inline text ("PIN incorrect. N attempts remaining before lockout."). 429 → "Too many attempts. Try again in Ns." with a live countdown until `retry_after_seconds` elapses. Mobile-safe (no hover-only affordances).

### Decision H — New existence-check endpoint

- `GET /api/settings/security/pin` returns `{ set: bool }`. Reason for existence: three destructive-action call sites need to know whether to render PinDialog or PhraseDialog. NEVER returns the hash or any per-user PIN state (no failure count, no lockout state — those come via the 429 response body from `/verify`).

### Refinement Notes

Real usage on prod stack (`make dev-prod` at `http://127.0.0.1:29090`) surfaced two issues that Build's unit tests missed:

**Bug 1 (backend — real safety-model bug): Post-cooldown 429 loop**
- Reproducer: 3 wrong PINs → 5s lockout. Wait past 5s. Correct PIN → still 429.
- Root cause: `InProcessPinRateLimiter.check()` used "failure count in 15-min sliding window" as the locked-vs-unlocked gate. Since 3 failures stay in the window for 15 min but the lockout duration is only 5s, `check()` returned "still locked" for the full window.
- Fix: `check()` now compares elapsed time since the LAST failure against the curve tier's `lockout_seconds`. Once the tier duration elapses, `check()` returns None (still counting toward the next tier if a new failure comes in). Ceiling-round the remaining seconds so we never report 0 while still locked.
- Tests added: `test_rate_limiter_check_clears_after_lockout_elapses` (cooldown elapses → check() → None), `test_rate_limiter_next_failure_after_lockout_escalates_tier` (post-cooldown next failure jumps to next tier).

**Bug 2 (UI): 429 lockout UX**
- ConfirmPinDialog rendered "PIN incorrect" (red) + "Try again in Ns" (amber) as two lines during lockout — confusing.
- After my first polish pass I introduced two new bugs: countdown `setInterval` never cleared (kept ticking and re-clearing the PIN input every second), and when countdown reached 0 the raw backend `"too_many_requests"` string re-appeared.
