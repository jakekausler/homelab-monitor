# STAGE-009-011: Auto-fix history UI — filterable table + transcript viewer + feedback display

## Status: Complete

## Overview

Build the Auto-fix history screen: a filterable table of `runbook_runs` (by runbook, mode, exit code, date), a transcript viewer that renders the full captured Claude session for a selected run, and the run metadata (exit code, durations, dry-vs-real, runbook hash). Also displays the improvement-feedback items (from STAGE-009-009) attached to each run. This is the read-only audit/observability surface for everything the orchestrator records.

**Vertical slice:** after this stage, the user can browse all auto-fix runs, filter them, open any run to read its full transcript + metadata, and see any improvement feedback the fixer emitted. Desktop + Mobile viewport sign-off.

**Spec references:** §9.1 (Auto-fix history nav entry), §9.2 (Auto-fix history screen — filterable table; row click opens transcript viewer with full Claude session, exit code, durations, before/after diff if generated), §7.4 (#4 audit — this is where the audit becomes visible). ## Concrete deliverables

### 1. Filterable runs table

`runbook_runs` table with filters (runbook, mode dry/real, exit code, date range). Columns: runbook, mode, exit code, started/ended, duration, alert.

### 2. Transcript viewer

Row click → full captured Claude session (transcript/stdout/stderr), exit code, durations, runbook hash. Read-only.

### 3. Feedback display

Show the `runbook_run_feedback` items (STAGE-009-009) for the selected run.

### 3.5. Runs aggregation endpoint (added during STAGE-009-010 Design 2026-07-02)

Expose an aggregation endpoint (`GET /api/runbooks/stats` or extend `GET /api/runbooks` with joined fields — Design phase decides) that returns per-runbook `last_run_at`, `last_run_status`, `success_rate_30d`, and `run_count_30d`. STAGE-009-010's Runbooks catalog cards render em-dash placeholders for these fields today; this deliverable wires them up.

### 4. Tests + sign-off

Vitest: table renders + filters; row opens transcript; feedback items display; no delete affordance present; catalog card stats endpoint returns valid summary; the STAGE-009-010 catalog cards render the new stats (integration verified in a small e2e / snapshot test). Desktop + Mobile viewport sign-off.

## Design Phase

**Status**: [x] Design (Complete)

### Design Notes (2026-07-03)

**Autonomous loop:** Design decisions selected by the implementing session (this loop runs
without user prompts during Design; recommendations validated against code-reality checks
before selection).

**Decision A — Route path & page structure: A1 — top-level `/autofix/history`.**
Rationale: safety-model non-negotiable #4 (audit) makes the runs history a first-class
surface; SidebarNav.tsx:51 already reserves the slot ("Auto-fix history — Coming soon");
stable URL enables deep-linking transcripts and future audit exports. Page structure:
`RunsHistoryPage` — filter bar (runbook selector, mode filter, exit-code filter, date-range
picker) → filterable runs table below → click a row navigates to `/autofix/history/:run_id`.

**Decision B — Transcript viewer UX: B3 — dedicated `/autofix/history/:run_id` route.**
Rationale: Claude session transcripts are long (multi-KB); a full-viewport route gives them
the room they need without cramping the list. Deep-linkable + shareable (audit/support flows).
Back-button semantics free from TanStack Router. Transcript rendered as plain `<pre>` +
monospace font (a Claude session dump isn't a lexable language; syntax-highlighting adds
maintenance for zero user value). Layout: metadata card (runbook, mode badge, exit code,
started/ended, duration, hash, initiator, alert linkage) → transcript `<pre>` panel →
feedback items panel (0-N rows from `runbook_run_feedback`).

**Decision C — Aggregation endpoint shape: C1 — new sibling `GET /api/runbooks/stats`.**
Rationale: history page needs the aggregation independently of the catalog; extending
`GET /api/runbooks` would couple catalog cache TTL to stats TTL (invalidating stats after
a new run would nuke the definition cache too). C1 is a single SQL `GROUP BY runbook_id`
scan over `runbook_runs`, feeds BOTH surfaces (history header + 010's catalog cards),
and gives history-specific query keys (`runbookStatsKeys.all = ['runbook-stats']`) that
can be invalidated by a manual "Run fix" completion (STAGE-009-010A hook) without
disturbing runbook definitions. Response shape:
`{ items: [{ runbook_id, last_run_at, last_run_status, success_rate_30d, run_count_30d }] }`
where `last_run_status` is one of `success`|`failure`|`killed`|`in_flight`|`dry_run` derived
from `exit_code` + `killed_at` + `mode` + `ended_at` (there is NO `outcome` column on
`runbook_runs` — verified against migrations 0045/0048/0050).

**Decision D — Date-range default: D3 — 30 days.**
Rationale: matches the `success_rate_30d` window shown on catalog cards; a user comparing
"success rate 82%" on a card must see the same rows in the history table. Filter accepts
custom ranges via a two-input date picker.

**Decision E — Pagination: E1 — offset (`?limit=100&offset=N`).**
Rationale: single-user tool with auto-fix defaulting to OFF; volume is measured in tens
to low hundreds per month; simpler URL semantics (page numbers land in the URL); B3's
detail route (`/autofix/history/:run_id`) fetches by ID and bypasses pagination position,
so deep-linking a transcript never depends on which page it's on. Default `limit=100`.

**Ancillary decisions (from code-reality verification):**
- **Outcome derivation** (no schema column exists): `in_flight` (`ended_at IS NULL AND killed_at IS NULL`),
  `killed` (`killed_at IS NOT NULL`), `success` (`ended_at IS NOT NULL AND exit_code = 0`),
  `failure` (`ended_at IS NOT NULL AND exit_code != 0`). Mode (`dry_run`/`real`) is always
  a distinct badge — never blends into outcome.
- **Dry-run visual distinction (non-negotiable #5):** every table row gets a mode badge;
  the detail page has a top-of-page banner ("Dry-run — plan only" vs "Real run") in
  contrasting colors. Dry-run detail pages surface a link to the approvals surface.
- **Operator-initiated runs** (`initiated_by='operator' AND alert_id IS NULL`, per 010A
  regression item 5): the initiator column shows "operator" for these rows; the alert
  column shows "—" (dash) for these rows without filtering them out. Alert filter is
  `alert / operator / any`.
- **Denied runs are OUT OF SCOPE:** kill_switch / allow_list / rate_limit / cooldown /
  etc. denials write only `audit_log` (not `runbook_runs`) — those live in a future
  audit-log viewer stage (not this one). STAGE-009-011 shows only what is in
  `runbook_runs`.
- **Feedback rows are display-only** — 0-N items per run; each renders `kind` badge +
  `suggestion_text` (bounded 4096 chars — no client truncation needed) + optional
  `structured_hint` details block; `kind='parse_error'` rows get a visually distinct
  "parse-error" badge.
- **Read-only surface enforcement (non-negotiable #4):** no delete/edit affordance on
  any run, transcript, or feedback item in the UI. Immutability is enforced backend-side
  in STAGE-009-012, but the UI must not offer deletion — regardless.

**Bug found + fixed during Refinement:** infinite loading on `/autofix/history` — root
