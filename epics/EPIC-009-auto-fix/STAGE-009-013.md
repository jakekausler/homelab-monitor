## Design Phase

### Design Notes (autonomous — selected by the implementing session, epic-loop)

**Approach: Option C — Hybrid.** Permanent regression pytest + one-shot Refinement-phase scripted validation on the prod rig. Selected by the implementing session (autonomous loop); brainstormer presented A/B/C. Rationale:
- Non-negotiables split cleanly across the two artifacts. The pytest covers #1 (allow-list match), #2 (scope envelope), #4 (audit), #5 (dry-run+approval), #6 (rate-limit/cooldown), #7 (kill switch) at code level with zero flake risk. The Refinement prod script closes the fidelity gap on #3 (identity — fake claude actually invoked as `homelab-fixer` inside the fixer-runner) and provides holistic HTTP-surface+subprocess+audit evidence.
- Prior stages already carry per-seam integration coverage (001/004/005/006/010A/010B/011/012/014/015/016/017). The pytest adds the missing "wired-together" test without duplicating per-seam coverage.
- Prod rig is the user's real monitor (`feedback_keep_rig_up.md`) — a permanent integration test mutating it every CI cycle is a category worth avoiding. One-shot Refinement validation with careful cleanup + recorded transcript is safer.

**Example runbook config (shipped verbatim).** Folder: `runbooks/_examples/pihole-restart-loop/`. Files: `runbook.yaml` + `CLAUDE.md`. YAML:

```
runbook: 1
name: pihole-restart-loop
match_patterns:
  - alertname: PiholeCrashLoop
risk_tag: risky
dry_run_required: true
rate_limit_per_hour: 2
cooldown_seconds: 900
scoped_capabilities:
  docker:
    container: pihole-unbound
    allowed_actions: [restart]
```

Conservative guard budget (2/hour, 15-min cooldown) fits exemplar-only ship-inert posture. `alertname: PiholeCrashLoop` is a synthetic alertname (no vmalert rule ships with this name); the user opts in by writing the rule + registering the runbook. `name: pihole-restart-loop` matches `RUNBOOK_NAME_PATTERN = ^[a-z][a-z0-9_-]{2,63}$`.

**CLAUDE.md content.** Runbook intent + allowed/forbidden actions per LOCKED Decision 2: allowed = `docker restart pihole-unbound` + tail its logs; forbidden = touching other containers or running other docker commands. Consumed by orchestrator as the Claude prompt body.

**Test file.** New pytest: `apps/monitor/tests/kernel/autofix/test_pihole_example_e2e.py`. Copies the shipped exemplar into `tmp_path` under a NON-underscore folder (so the loader picks it up), direct-registers via `RunbookRepo`, drives dry-run → approval → real-exec through the orchestrator's phase methods (mocked `DockerSocketClient`), asserts: (i) config validates against `RunbookConfig.load_from_path`, (ii) `_resolve_grants` returns docker envelope for `pihole-unbound` + `restart`, (iii) `_execute_intents` on a synthetic `docker-intent.json` calls the mock docker client, (iv) full audit trail written, (v) `GET /api/autofix/runs` includes the row.

**Ship-inert verification.** The loader's `folder.name.startswith("_")` skip is already covered by STAGE-009-004 tests; 013 adds an explicit assertion that scanning the repo-root `runbooks/` directory does NOT include `_examples/pihole-restart-loop` in `ScanResult.loaded`.

**History UI verification: API-only.** Stage adds NO new UI code — STAGE-009-011 already ships `RunsHistoryPage` + `RunsTable` + the `GET /api/autofix/runs` endpoint. API-only verification is sufficient; no Desktop+Mobile viewport signoff required.

**Refinement script (deferred to Refinement phase).** e2e-tester script on prod rig: copy folder → `POST /api/runbooks/refresh` → `PATCH /api/runbooks/{id}` enable → inject synthetic `PiholeCrashLoop` alert via `POST /api/alerts` → verify dry-run plan → PIN-approve via `POST /api/runbooks/runs/{id}/approve` → confirm real run invoked fake claude → verify `GET /api/autofix/runs` shows row → cleanup (delete folder → refresh → verify prune audit row from STAGE-009-017). Fake-claude transcript first-20-lines + `GET /api/autofix/runs` JSON response captured verbatim in this card during Refinement.

### Refinement Notes (autonomous, epic-loop)

Executed the end-to-end pipeline validation on prod instance A (`homelab-monitor` at `http://192.168.2.148:29090`) using a scratch copy of the shipped exemplar at `runbooks/pihole-restart-loop-e2e-stage013/` (`cooldown_seconds: 0` to work around the STAGE-009-013-regression-item-#1 dry-run-tripping-cooldown behavior). Six attempts total; attempts 1-5 blocked by distinct genuine defects, each fixed in-scope; attempt 6 passed cleanly end-to-end.

**Attempt 1** — blocked at `PATCH /api/runbooks/{id}` `{"auto_trigger":true}` returning `400 risky_auto_trigger_denied` (STAGE-009-010A defense-in-depth). Test script correction: enable with `{"enabled":true}` only (operator-initiated flow doesn't require `auto_trigger`).

**Attempt 2** — blocked at trigger returning `409 kill_switch`. Prod kill switch was OFF at baseline (correct). Test script correction: enable + disable kill switch via `POST /api/settings/autofix/kill-switch` with `confirm_phrase: "enable auto-fix"` / `"disable auto-fix"`.

**Attempt 3** — blocked at approve returning `409 allow_list`. **Genuine product defect discovered.** `AutoFixOrchestrator.execute_approved` (`orchestrator.py:1450`) called `_check_operational_gates(record)` without `require_auto_trigger=False`, asymmetric to `handle_operator_trigger`'s call at `orchestrator.py:1651`. Since STAGE-009-010A rejects `auto_trigger=True` on risky runbooks, the risky dry-run → approve → real-exec path was unreachable via the HTTP API. Fixed in-scope by patching `execute_approved` to pass `require_auto_trigger=False` (operator has already authenticated via PIN/phrase and the plan is content-hash-pinned; `auto_trigger` is an alert-routing concept). Added regression test `test_execute_approved_allows_operator_path_with_auto_trigger_false` in `test_autofix_orchestrator.py` (~line 3164).

**Attempt 4** — approve now returned `200 ran`, but the real-run process exited `1` in 5ms. **Second product-behavior discovery.** The pytest was a false-green because it uses `_FakeDockerClient` (in-process fake, no real exec); the API path exercises the ACTUAL `fake-claude` script. Root cause: `_configure_egress_for_exec` (STAGE-009-015) tried to `open("w")` `/data/proxy/allowlist.txt` and got `PermissionError` because `/storage/programs/homelab-monitor/deploy/compose/proxy/` was owned by uid 1000 (host user) but the monitor container runs as uid 995. Two artifact fixes: (a) host-side `sudo chown -R 995:995 /storage/programs/homelab-monitor/deploy/compose/proxy` (applied by user, 2026-07-04), (b) `_load_alert_for_exec` simplified (removed dead `alert_id: str | None` branch that became unreachable once `execute_approved`'s ternary short-circuits `None`).

**Attempt 5** — blocked at Step 1 login: e2e-tester subagent lost credentials context. Not a defect; retry.
