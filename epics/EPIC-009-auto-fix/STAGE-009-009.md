# STAGE-009-009: Claude→user improvement-feedback channel

## Status: Complete

## Overview

Build the improvement-feedback channel (LOCKED Decision 3): when the fixer hits a limitation and exhausts its options, OR finishes but had to work around something inefficiently, it emits **structured feedback** ("this would've gone better with capability X / config change Y") that the orchestrator captures, persists, and the UI surfaces for the user to review. The user can then decide whether to adjust the runbook's configuration. This is a NEW first-class concept with no downstream consumer yet (purely additive — it does not change any existing contract).

**Vertical slice:** after this stage, a fixer run that emits structured feedback (via the agreed output contract) produces persisted feedback rows linked to the run, and the user can see them in the Auto-fix UI. A run with no feedback produces none.

**Spec references:** EPIC-009 LOCKED Decision 3. §3.1 (runbook orchestrator captures run output — extended here to parse a structured feedback marker). §6.1 (a new sibling table alongside `runbook_runs`). §9.2 (Auto-fix history screen — the review surface).

## Concrete deliverables

### 1. Structured feedback output contract

Define how the fixer signals feedback: a sentinel feedback file in its transcript dir (e.g. `feedback.json`) OR a structured stdout marker the orchestrator parses. Document the schema (what fields: a free-text suggestion, an optional structured "wanted capability / config change" hint, a severity/kind).

### 2. Persistence (`runbook_run_feedback` sibling table)

A new migration: `runbook_run_feedback` (id, runbook_run_id FK, kind, suggestion_text, structured_hint JSON, created_at). Multiple feedback items per run. Linked to the run + (transitively) the runbook.

### 3. UI review surface

Surface feedback items in the Auto-fix UI (the run-detail / history view). The user reads them and can decide to adjust the runbook config. (If Design folds this into STAGE-009-011, document that.)

### 4. Tests

Fake claude emits a feedback marker → parsed → persisted → linked to the run; multiple items per run; a run with no feedback → no rows; malformed feedback marker → recorded as an error, not a crash.

## Design Phase

**Status**: [x] Design (Complete)

### Design Decisions (autonomous loop — implementer selected)

The following decisions were made by the implementing session in the autonomous
epic-stage-workflow loop (no user prompt during Design; user retains veto in
Refinement). Rationale is captured verbatim from the brainstormer output.

**Decision A — Feedback output contract shape: A1 (sentinel file in transcript dir)**

The fixer writes ONE `<pid>.feedback.json` file into `HOMELAB_MONITOR_FIXER_TRANSCRIPT_DIR`
(same PID-prefixed attribution pattern the fake claude already uses for
`<pid>.transcript`). The file contains a JSON array of feedback items (may be empty).
The orchestrator scans the transcript dir for `*.feedback.json` files created during
the run window (mirror of `_resolve_transcript` at `orchestrator.py:1263-1292`).

Rejected: A2 (structured stdout marker) — real `claude` invokes a Node subprocess
whose stdout marker discipline is not under our control; coupling feedback parsing
to real-claude stdout hygiene is fragile. Rejected: A3 (JSON-lines in transcript) —
overloads the transcript's semantic (the raw audit artifact per safety non-negotiable
#4); a change in transcript format would break both audit and feedback channels.

**Decision B — `runbook_run_feedback` schema shape**

- `id`: `TEXT` primary key, UUIDv7 from `homelab_monitor.kernel.db.ids.uuid7()`
  (matches `runbook_runs.id` convention).
- `runbook_run_id`: `TEXT NOT NULL`, FK → `runbook_runs.id`. No `ondelete="CASCADE"`
  (matches existing FK convention in migrations 0045-0047 — bare FK named
  `fk_runbook_run_feedback_runbook_run_id`).
- `kind`: `TEXT NOT NULL`. Python-side StrEnum `FeedbackKind` in
  `apps/monitor/homelab_monitor/kernel/autofix/types.py` (matching the existing
  `DenialReason` / `RunOutcome` / `RunMode` pattern), values:
  `missing_capability`, `config_change`, `runbook_gap`, `blocked`, `worked_around`,
  `other`, `parse_error`. Validated at the repo layer, persisted as string.
- `suggestion_text`: `TEXT NOT NULL`. Bounded to 4096 chars at persist time;
  overflow truncated with `\n...[truncated]` suffix.
- `structured_hint`: `TEXT NULL` (SQLite JSON as TEXT). Loose documented schema —
  a Pydantic-model-with-`dict[str, Any]` field. Docstring lists expected keys per
  kind (e.g., `missing_capability` → `{"capability_name": str, "example_command":
  str?}`). No runtime discrimination — 011 will discover what shapes it actually
  needs to render and can propose a schema tightening then.
- `created_at`: `TEXT NOT NULL`, ISO-8601 UTC (matches `runbook_runs.created_at`).

Index: `ix_runbook_run_feedback_runbook_run_id ON runbook_run_feedback(runbook_run_id)`
(for cheap per-run lookups from STAGE-009-011's history view).

Rejected: B1 free-text kind (typos leak to UI). Rejected: B2 SQL CHECK enum (SQLite
enforcement is weak; migration cost per new kind). Rejected: discriminated-union
`structured_hint` (over-engineered — no downstream consumer yet).

**Decision C — Malformed feedback handling: C3 (both row + audit)**

When the sentinel file exists but fails to parse (invalid JSON, wrong top-level
type, item missing `kind`/`suggestion_text`), the orchestrator persists ONE synthetic
feedback row with `kind="parse_error"`, `suggestion_text="<raw content, truncated
to 4KB>"`, `structured_hint=null`, AND emits an audit_log entry
`autofix.feedback_parse_error` referencing the row's id and the parse error
message. This gives the user immediate visibility (UI, when 011 lands) while
preserving audit-trail integrity per non-negotiable #4.

Rejected: C1 (row only) — weakens audit observability. Rejected: C2 (audit only) —
zero user visibility defeats the whole point of the channel.

**Decision D — UI split with STAGE-009-011: D1 (backend-only in 009; UI to 011)**

STAGE-009-009 delivers backend only (parser + sibling table + migration + repo +
orchestrator seam + fake-claude extension + tests). NO UI in this stage. NO API
route in this stage. NO shared-types regen from this stage.

Rationale: STAGE-009-011's title is "Auto-fix history UI — filterable table +
transcript viewer + feedback display" and its Deliverable #3 explicitly reads:
"Show the `runbook_run_feedback` items (STAGE-009-009) for the selected run."
011 also owns the backend read-side (`/api/autofix/runs`); NEITHER exists yet.
Building temporary UI in 009 forces us to invent a throwaway read endpoint that
011 replaces. Feedback rows are safely persisted and queryable via SQLite CLI in
the (brief) gap between 009 landing and 011 starting.

This is NOT a silent deferral — the receiving stage is a concrete tracked stage
that already exists with the feedback display as an explicit deliverable. The
`Refinement > Frontend viewport sign-off` checkbox becomes N/A for 009. This
adjustment is noted below in Refinement.
