# STAGE-010-010: First synthetic shadow pair (vmalert-vs-vmalert on host CPU)

## Status: Not Started

## Overview

Per EPIC-010 Decision 6 (locked 2026-07-05), ship a synthetic first shadow pair to prove the framework works end-to-end without waiting for EPIC-015 (Netdata). Pair two vmalert rules on `homelab_host_cpu_percent`: a strict threshold (`HostCriticalCPU`, already exists in `host.yaml`) vs a baseline anomaly rule (`HostCPUAnomalous`, already exists in `host_anomalies.yaml`).

Both rules already fire on prod (verified 2026-07-05 recon). Their overlap is a genuine test of the framework: when CPU truly spikes, both fire → high `both_hits`. When only the anomaly fires (subtle drift) → high `disagreement_count`. When only the threshold fires (fast burst under the anomaly's baseline window) → also disagreement.

## Concrete deliverables

1. Add the pair to `deploy/shadow-pairs.yaml`:
   ```yaml
   shadow_pairs:
     - name: host_cpu_strict_vs_baseline
       description: "Threshold rule (strict) vs baseline anomaly rule on host CPU"
       rule_a:
         source_tool: vmalert-metrics
         alertname: HostCriticalCPU
       rule_b:
         source_tool: vmalert-metrics
         alertname: HostCPUAnomalous
   ```
2. Verify the framework's overlap join strategy (decided during 009 Design) produces correct results for this pair on prod data. If the two rules produce non-matching fingerprints (likely — different alertnames = different fingerprints), the framework must join by `instance` label + time window rather than by fingerprint. Confirm during Design + Refinement.
3. Verify the Tool Analysis UI's ShadowRuleComparisonPanel renders sensible numbers for this pair on prod.
4. Test coverage:
   - Fixture DB with the two rules' alerts produces expected `both_hits` / `disagreement_count`.
   - Prod-side sanity check: run the aggregator against prod's actual alert history, verify counts are non-zero and match manual SQL for either rule.
