# STAGE-010-004: One-shot backfill CLI for existing alert outcomes

## Status: Not Started

## Overview

Retrofit for the 168k `alerts` rows in prod that pre-date STAGE-010-003's reconciler. Without backfill, scorecards for EPIC-001..009 + 017 rules would show empty action-rates until enough new outcome data accumulates through the hourly reconciler (weeks minimum).

Per EPIC-010 Decision 3 (locked 2026-07-05), a one-shot `hm alerts backfill-outcomes` CLI subcommand infers outcomes deterministically from existing `alerts` column state: `ack_at IS NOT NULL` → `AlertOutcome.ACKED`; `resolved_at IS NOT NULL AND ack_at IS NULL` → `AlertOutcome.AUTO_RESOLVED`; still-firing alerts get no outcome row (they're not decided yet).

**Retrofit for:** EPIC-001..009 + 017.

## Stage Flags

- Has Input Forms: [ ] No
- Touches secrets / production data: [x] Yes — INSERTs O(100k) rows into `alert_outcomes` on prod. Idempotent + self-guarding.
- Host-integration concerns: [ ] No — CLI runs against the DB directly.

## Concrete deliverables

1. New `hm` subcommand `hm alerts backfill-outcomes` under `apps/monitor/homelab_monitor/cli/`:
   - `--dry-run` reports what WOULD be written without touching the DB.
   - `--confirm-phrase="backfill outcomes from historical alert state"` required for the real run.
   - Refuses to run if `alert_outcomes` already has ANY rows where `decided_by != "backfill"` (guards against running AFTER the reconciler starts producing real outcomes — would corrupt the natural signal).
   - Refuses to run if it has been run before (checks for existence of ANY row with `decided_by = "backfill"`).
2. Backfill logic (single SQL transaction):
   - `INSERT INTO alert_outcomes (id, alert_id, outcome, decided_at, decided_by) SELECT uuid7(), id, 'acked', ack_at, 'backfill' FROM alerts WHERE ack_at IS NOT NULL;`
   - `INSERT INTO alert_outcomes (id, alert_id, outcome, decided_at, decided_by) SELECT uuid7(), id, 'auto_resolved', resolved_at, 'backfill' FROM alerts WHERE resolved_at IS NOT NULL AND ack_at IS NULL;`
   - Writes ONE `audit_log` row summarizing the operation: `who = "cli:hm-alerts-backfill-outcomes"`, `what = "alert_outcomes_backfilled"`, `after = {acked_count, auto_resolved_count, total, at}`.
3. Progress reporting: for large batches (>10k rows), print progress every 10k rows.
4. Test coverage:
   - Dry-run reports expected counts on a fixture DB.
   - Real run without confirm-phrase aborts.
   - Successful run writes expected rows + audit row + is not repeatable.
   - Second run after successful first refuses with clear error.
   - Second run after ANY non-backfill row exists refuses with clear error.
   - Fixture DB with mixed states verifies each mapping branch.
5. Prod-side execution (Refinement):
   - Run `--dry-run` FIRST, capture the counts.
   - Run under supervision with `--confirm-phrase`.
   - Verify `alert_outcomes` populated + audit_log row present.
   - Verify STAGE-010-003 reconciler still works (won't touch rows the backfill produced because idempotent INSERT OR IGNORE covers all `(alert_id, outcome)` pairs).
