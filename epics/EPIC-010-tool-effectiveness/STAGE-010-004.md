# STAGE-010-004: One-shot backfill CLI for existing alert outcomes

## Status: Complete

## Overview

Retrofit for the 168k `alerts` rows in prod that pre-date STAGE-010-003's reconciler. Without backfill, scorecards for EPIC-001..009 + 017 rules would show empty action-rates until enough new outcome data accumulates through the hourly reconciler (weeks minimum).

Per EPIC-010 Decision 3 (locked 2026-07-05), a one-shot `hm alerts backfill-outcomes` CLI subcommand infers outcomes deterministically from existing `alerts` column state: `ack_at IS NOT NULL` → `AlertOutcome.ACKED`; `resolved_at IS NOT NULL AND ack_at IS NULL` → `AlertOutcome.AUTO_RESOLVED`; still-firing alerts get no outcome row (they're not decided yet).

**Retrofit for:** EPIC-001..009 + 017.

## Stage Flags

- Has Input Forms: [ ] No
- Touches secrets / production data: [x] Yes — INSERTs O(100k) rows into `alert_outcomes` on prod. Idempotent + self-guarding.
- Host-integration concerns: [ ] No — CLI runs against the DB directly.

## Concrete deliverables

1. New `hm` subcommand `hm alerts backfill-outcomes` under `apps/monitor/homelab_monitor/cli/`:
   - `--dry-run` reports what WOULD be written without touching the DB.
   - `--confirm-phrase="backfill outcomes from historical alert state"` required for the real run.
   - Refuses to run if `alert_outcomes` already has ANY rows where `decided_by != "backfill"` (guards against running AFTER the reconciler starts producing real outcomes — would corrupt the natural signal).
   - Refuses to run if it has been run before (checks for existence of ANY row with `decided_by = "backfill"`).
2. Backfill logic (single SQL transaction):
   - `INSERT INTO alert_outcomes (id, alert_id, outcome, decided_at, decided_by) SELECT uuid7(), id, 'acked', ack_at, 'backfill' FROM alerts WHERE ack_at IS NOT NULL;`
   - `INSERT INTO alert_outcomes (id, alert_id, outcome, decided_at, decided_by) SELECT uuid7(), id, 'auto_resolved', resolved_at, 'backfill' FROM alerts WHERE resolved_at IS NOT NULL AND ack_at IS NULL;`
   - Writes ONE `audit_log` row summarizing the operation: `who = "cli:hm-alerts-backfill-outcomes"`, `what = "alert_outcomes_backfilled"`, `after = {acked_count, auto_resolved_count, total, at}`.
3. Progress reporting: for large batches (>10k rows), print progress every 10k rows.
4. Test coverage:
   - Dry-run reports expected counts on a fixture DB.
   - Real run without confirm-phrase aborts.
   - Successful run writes expected rows + audit row + is not repeatable.
   - Second run after successful first refuses with clear error.
   - Second run after ANY non-backfill row exists refuses with clear error.
   - Fixture DB with mixed states verifies each mapping branch.
5. Prod-side execution (Refinement):
   - Run `--dry-run` FIRST, capture the counts.
   - Run under supervision with `--confirm-phrase`.
   - Verify `alert_outcomes` populated + audit_log row present.
   - Verify STAGE-010-003 reconciler still works (won't touch rows the backfill produced because idempotent INSERT OR IGNORE covers all `(alert_id, outcome)` pairs).

## Design Phase

**Status:** [x] Complete (2026-07-07)

**Decided autonomously by the implementing session** (per epic-loop standing procedure — this loop is autonomous; the session decides during Design and does not prompt the user). All decisions below are locked; Build proceeds against them exactly.

### Selected approach — summary

Extend the existing `alerts` subparser in `apps/monitor/homelab_monitor/cli/alerts.py` with a second subcommand `backfill-outcomes`. Mirror the STAGE-010-001 `purge` command's shape end-to-end: same `--dry-run` / `--confirm-phrase` validation pattern, same async-handler-wrapped-in-`asyncio.run` pattern, same one-transaction-via-`repo.transaction()` shape, same `insert_audit` call for a single summary audit row.

### Design decisions (locked)

**D1. CLI location + registration.** Register the new subparser inside the existing `add_subparser` function in `apps/monitor/homelab_monitor/cli/alerts.py` (do NOT create a new file). The `alerts` namespace already exists; just add another `sub.add_parser("backfill-outcomes", ...)`.

**D2. Confirm-phrase constant.** `_EXPECTED_BACKFILL_CONFIRM_PHRASE = "backfill outcomes from historical alert state"`. Validation uses the same `.strip().casefold()` comparison as `_cmd_purge` (mirrors `PhraseMatchMode.CASE_FOLD`).

**D3. UUID generation strategy — Python `uuid7()` per row via SQLAlchemy executemany.** SQLite has no built-in `uuid7()`, and no UDF is registered anywhere in the codebase (verified by grepping for `create_function`, `register_function`, `create_scalar_function` — zero hits). All existing `alert_outcomes` writers (`AlertRepository.insert_outcome`, `AlertRepository.insert_outcome_if_absent`, `autofix/orchestrator.py::_insert_outcome_conn`) call the Python-side `homelab_monitor.kernel.db.ids.uuid7()` once per row. The backfill mirrors that: build `list[dict]` of param bindings with `"id": uuid7()` per row and pass to `conn.execute(stmt, params_list)` for SQLAlchemy executemany. This means the deliverable's SQL is executed in two steps per outcome type (query + INSERT executemany), not as a single `INSERT ... SELECT uuid7() ...`. The end DB state is identical to the card's spec.

**D4. Execution shape — two-pass query + executemany, single transaction.**
Inside one `async with repo.transaction() as conn:` block:
  1. `SELECT id, ack_at FROM alerts WHERE ack_at IS NOT NULL` → build param list with `uuid7()`, `decided_at=ack_at`, `decided_by="backfill"`, `outcome="acked"`.
  2. executemany INSERT with ON CONFLICT DO NOTHING (same SQL as `AlertRepository.insert_outcome`).
  3. `SELECT id, resolved_at FROM alerts WHERE resolved_at IS NOT NULL AND ack_at IS NULL` → build param list, `outcome="auto_resolved"`.
  4. executemany INSERT with ON CONFLICT DO NOTHING.
  5. Single `insert_audit` summary row.
Atomicity guaranteed by the outer transaction; any failure rolls back both INSERT passes AND the audit row.

**D5. SQL statement — reuse canonical column tuple.**
```
INSERT INTO alert_outcomes
  (id, alert_id, outcome, decided_at, decided_by, created_at)
VALUES (:id, :aid, :outcome, :dt, :db, :created)
ON CONFLICT (alert_id, outcome) DO NOTHING
```
- `decided_at` = the alert's `ack_at` (ACKED path) or `resolved_at` (AUTO_RESOLVED path) — semantic anchor, matches `insert_outcome_if_absent`'s convention.
- `created_at` = `utc_now_iso()` — persistence time.
- `decided_by = "backfill"` — sentinel string (widened from int in migration 0053).

**D6. Idempotency guard — LOCKED interpretation (OVERRIDES stale card wording).**

The stage card was authored BEFORE STAGE-010-003 landed. When the card was written, `alert_outcomes` was empty (0 rows), so the card's guard phrasing "refuses if `decided_by != 'backfill'` rows exist" was a valid one-shot check. As of STAGE-010-003 close (2026-07-07T03:34Z), prod `alert_outcomes` has 13,973 rows, ALL `decided_by='reconciler'` — the reconciler's legitimate output. The stale card wording would refuse to run against every prod DB going forward, which is not the intent.

**Locked guard interpretation:**
- The one-shot semantic is: "has this backfill CLI ever been run before?" — NOT "is `alert_outcomes` empty of external writes?"
- Guard = "refuse to run if ANY row with `decided_by='backfill'` exists" (single unambiguous check).
- Reconciler rows (`decided_by='reconciler'`) or auto-fix rows (`decided_by='autofix'`) or any future provenance MUST NOT trigger refusal.
- Overlap between reconciler AUTO_RESOLVED rows and backfill AUTO_RESOLVED rows for the same `(alert_id, 'auto_resolved')` is silently handled by `ON CONFLICT (alert_id, outcome) DO NOTHING` — the reconciler's row wins (it was there first), backfill silently skips.
- Backfill ACKED rows have zero expected collisions on current prod (0 ACKED rows exist).
- A future re-run after schema wipe / fresh DB would work fine (no backfill row → guard passes).

**D7. Audit log — single summary row via `insert_audit`.**
```python
await insert_audit(
    conn,
    who="cli:hm-alerts-backfill-outcomes",
    what="alert_outcomes_backfilled",
    before=None,
    after={
        "acked_count": <int>,
        "auto_resolved_count": <int>,
        "total": <acked + auto_resolved>,
        "at": utc_now_iso(),
        "backfill_source": "alerts_row_state",
    },
)
```
One row for the whole operation. Written on every real run including zero-match runs (matches purge precedent). NOT written for `--dry-run`. The `after` field carries the summary; `before` is `None` because there is no pre-state (backfill only writes, never mutates).

**D8. Progress reporting.**
Card spec: "for large batches (>10k rows), print progress every 10k rows." Implementation: during the SELECT-to-param-list build phase for each outcome type, print a progress line every 10,000 rows processed. At prod scale (~14k acked + a fraction of that for auto_resolved rows, minus reconciler overlap), expect 1-2 progress lines total. If total row count for a pass is ≤10,000, no intermediate progress line (just the final summary).

**D9. Dry-run behavior.**
Runs the two SELECT queries (or their `COUNT(*)` equivalents), reports:
```
Dry run: would insert {acked_count} ACKED + {auto_resolved_count} AUTO_RESOLVED = {total} alert_outcomes rows. No DB changes made.
```
Exits 0. No INSERTs. No audit_log row.

**D10. Exit codes.**
- `0` — success (real run committed, or dry-run completed).
- `1` — validation error: missing `--dry-run` and no `--confirm-phrase`; wrong confirm-phrase; already-run guard tripped (backfill row exists).

**D11. Test coverage (with HANDOFF corrections applied).**
The card's test coverage bullets are followed with two corrections:
1. The card's "second run after ANY non-backfill row exists refuses" test is REPLACED with the guard-appropriate test: "second run after a `decided_by='reconciler'` row exists does NOT refuse — writes fresh backfill rows and uses ON CONFLICT DO NOTHING for any AUTO_RESOLVED overlap." (Direct consequence of D6.)
2. Fixture DB must include an already-reconciler-written AUTO_RESOLVED row for one of the fixture alerts, verifying the ON CONFLICT skip path.

Full test list:
- Dry-run reports expected counts on fixture DB (no writes).
- Real run without `--dry-run` and without `--confirm-phrase` aborts with clear error, exit 1.
- Real run with wrong `--confirm-phrase` aborts with clear error, exit 1.
- Successful real run writes expected rows + one summary audit_log row + exits 0.
- Second real run after successful first refuses with clear error (backfill row exists), exit 1.
- Second real run after only reconciler-written rows exist does NOT refuse — writes fresh rows, ON CONFLICT skips reconciler-overlap AUTO_RESOLVED alerts.
- Fixture DB with mixed states (acked-only, resolved-only, both-set, still-firing, already-reconciled AUTO_RESOLVED) verifies each mapping branch AND the ON CONFLICT skip path.

- Whether progress printing uses `print(...)` or `structlog` INFO or both — Build will match purge precedent (which uses `structlog.info` for the committed event + `print(...)` for user-facing messages).
- Test file location: `apps/monitor/tests/cli/test_alerts_backfill_outcomes.py` (following `test_alerts_purge.py` if it exists) — Build confirms.
