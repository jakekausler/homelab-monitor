# STAGE-010-009: Shadow-rule framework

## Status: Not Started

## Overview

Ship the shadow-rule framework — a way to run two detectors in parallel on the same underlying signal and compare hit / miss / disagreement rates. Analyzer surfaces the comparison so the user can decide "detector A is doing all the work; disable B" or "they disagree 40% of the time; investigate."

Framework only in this stage. First synthetic pair in STAGE-010-010. First REAL pair (Netdata anomaly vs vmalert baseline) is scheduled for EPIC-015 per the integration note in EPIC-010.md.

## Concrete deliverables

1. Config schema for shadow pairs. New file `deploy/shadow-pairs.yaml`:
   ```yaml
   shadow_pairs:
     - name: host_cpu_strict_vs_baseline
       description: "Threshold rule (strict) vs baseline anomaly rule on host CPU"
       rule_a:
         source_tool: vmalert-metrics
         alertname: HostCriticalCPU
       rule_b:
         source_tool: vmalert-metrics
         alertname: HostCPUAnomalous
   ```
   Loader validates on startup; malformed config surfaces as a plugin-loader error.
2. Framework module `kernel/analyzer/shadow.py`:
   - For each pair × window, compute:
     - `rule_a_hits` — count of alerts matching rule_a criteria.
     - `rule_b_hits` — count of alerts matching rule_b criteria.
     - `both_hits` — count of alerts where BOTH detectors fired within group_interval (5m) for the same target instance (join by `instance` label OR by fingerprint intersection — decide during Design based on whether the two rules produce alerts with matching fingerprints).
     - `either_hits` — count of alerts where EITHER fired.
     - `disagreement_count` — `either_hits - both_hits`.
   - Writes to `shadow_rule_results` table.
   - Runs nightly, sequenced after `scorecard_aggregator`.
3. Backend `GET /api/shadow-rule-results`:
   - Query params: `pair_name` (optional), `window` (default `30d`).
   - Response: `{items: ShadowRuleResultOut[]}`.
   - Session auth.
4. Frontend `ShadowRuleComparisonPanel.tsx`:
   - Component rendered on the Tool Analysis page below the cards grid.
   - For each configured pair, shows a compact comparison: rule_a hits, rule_b hits, overlap count, disagreement count, and a Venn-diagram-style visualization (SVG, not a library — small enough).
   - Empty state if no pairs are configured.
5. Test coverage:
   - Config load with valid + invalid pairs (validation error surfaces).
   - Fixture DB with known alert distribution across two rules produces expected result row.
   - Idempotent recompute overwrites previous result row.
   - Empty pair (no alerts on either rule) writes a row with zeros (not skipped — user needs to see "nothing has fired yet").
   - Backend endpoint returns paginated results.
   - Frontend renders panel with test data.
