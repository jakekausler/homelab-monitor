# STAGE-010-006: Nightly aggregation job (multi-dimensional scorecards)

## Status: Not Started

## Overview

Compute the scorecards. Per EPIC-010 Decision 1, aggregate across FIVE orthogonal dimensions × THREE windows: `source_tool` (4 values × 3), `category` (12 × 3), `target_kind` (10 × 3), `alertgroup` (39 × 3), `alertname` (86 × 3). ~453 scorecard rows per full run. Nightly cadence, `analyzer` concurrency group, low ionice priority.

For each (dimension, dimension_value, window) row, compute:

- `alerts_emitted` — COUNT of alerts where the row's `alerts.payload_json.labels[dimension] == dimension_value` (for source_tool + severity, from indexed columns) within the window.
- `action_rate` — fraction of those alerts whose `alert_outcomes.outcome` is in {`acked`, `dismissed`, `auto_fixed`, `escalated`}. `auto_resolved` and `maintenance_suppressed` are NOT counted as user action; still-open alerts drop out of denominator.
- `dedup_overlap` — fraction of those alerts whose fingerprint appears in an `alert_overlap_groups` row that ALSO contains an alert from a DIFFERENT `dimension_value` at the same dimension. (I.e., "of my alerts, how many were also caught by someone else?")
- `unique_share` — 1 - `dedup_overlap`, but with the constraint that "someone else" only counts if they're the same dimension. Distinct: unique to THIS dimension_value at THIS dimension.

## Concrete deliverables

1. New collector `scorecard_aggregator` under `kernel/analyzer/`:
   - Runs nightly (default 03:00 host TZ, configurable).
   - `concurrency_group: analyzer`, `run_kind: PROCESS` (CPU-bound over 168k+ rows, benefits from process isolation), low ionice priority.
   - Requires STAGE-010-007 (overlap groups) to be complete for `dedup_overlap` + `unique_share` computation; the collector should degrade gracefully (write scorecards with only `alerts_emitted` + `action_rate` if overlap groups are missing, plus a `NULL` for overlap dimensions, so the UI can still render partial data during a bootstrapping period).
2. Query strategy for label-based dimensions:
   - For `source_tool` and `severity`: use the indexed row columns directly.
   - For `alertname`, `alertgroup`, `category`, `target_kind`, `anomaly_kind`: extract via SQLite `json_extract(payload_json, '$.labels.<key>')`. Decide during Design whether to add promoted columns (per label) with a data-migration pass, or accept the JSON-extract overhead. Trade-off: adding columns is a schema change + migration cost; JSON extract is per-query CPU. Given nightly cadence + ~168k rows, JSON extract is probably fine — verify during Design with an EXPLAIN QUERY PLAN.
3. Scheduler alerts (source_tool='scheduler', payload_json.labels empty): special-case handling. These have `source_tool = 'scheduler'` in the row column but NO `alertname` / `alertgroup` / `category` / `target_kind` in the labels dict. Fall back to synthesizing a synthetic `alertname='collector_quarantined'` value from the `payload_json` fields the scheduler DOES set. Document in the collector's docstring.
4. Idempotent writes: each nightly run computes fresh scorecards and REPLACEs any existing rows for the current `computed_at` window boundary. The UNIQUE INDEX from STAGE-010-002 enforces the invariant.
5. Test coverage:
   - Fixture DB with known alerts + outcomes produces expected scorecard values.
   - `action_rate` correctly excludes `auto_resolved` from numerator but keeps in scope.
   - `alerts_emitted` window boundary is inclusive on start, exclusive on end (or the other convention — pick one and document).
   - Scheduler-source alerts still produce a scorecard row.
   - Second run overwrites first for the same (dimension, dimension_value, window) without duplicating.
