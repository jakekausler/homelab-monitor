## Design Notes

**Autonomous loop.** All decisions below made by the implementing session per epic-loop standing procedure. No user prompt during Design.

### Diagnosis (three hypotheses, all confirmed)

Prod-DB reality at Design time: `alert_outcomes` has 14,222 rows (reconciler=14,219, backfill=3), zero with `outcome='auto_fixed'`. Three hypotheses explain the 0-count:

- **(a) Latent code bug.** CONFIRMED. `_insert_outcome_conn` at `orchestrator.py:2141` hardcodes `"db": None`, writing NULL to `decided_by` instead of `'autofix'`. The method signature has no `decided_by` parameter — it's a value that's always the same string ("autofix"), but the string is missing.
- **(b) No successful auto-fix on prod.** PARTIALLY TRUE. STAGE-009-013's real-mode prod E2E ran successfully (exit_code=0) but was operator-initiated (dry-run with `alert_id=NULL`), which triggers hypothesis (c).
- **(c) `alert is not None` guard skips writes for alertless runs.** CONFIRMED. `_persist_outcome` at `orchestrator.py:2049` gates the outcome write on `exec_result.exit_code == 0 and alert is not None`. STAGE-009-013's alertless operator-initiated run hit this branch and wrote no outcome row.

The combination of (a) and (c) means: even if (b) were false (some alert-linked auto-fix had run), the outcome row would have `decided_by=NULL` and scorecards would not be able to attribute it. Both fixes must land BEFORE Refinement's prod E2E can meaningfully validate.

### Caller audit (standing rule — twice-learned)

Every writer to `alert_outcomes` audited during Design (rule: schema/constraint change requires all-writer audit):

| Writer | File:Line | `decided_by` value |
|---|---|---|
| `AlertRepository.insert_outcome` | `kernel/alerts/repository.py:306` | Parameter passthrough (`str \| None`) — correct |
| `AlertRepository.insert_outcome_if_absent` | `kernel/alerts/repository.py:362` | Parameter passthrough (`str \| None`) — correct |
| `AutofixOrchestrator._insert_outcome_conn` | `kernel/autofix/orchestrator.py:2113` | **Hardcoded `None`** — bug |
| `_cmd_backfill_outcomes` CLI | `cli/alerts.py:32,301,317` | Hardcoded `"backfill"` — correct |

Call sites that supply `decided_by` to the AlertRepository writers all pass a provenance string: `"karma"` (silences reconciler), `"reconciler"` (resolutions reconciler), `str(user.id)` (ack/dismiss API), `"backfill"` (CLI). Only the autofix path is missing its provenance string. Scope stays narrow: fix `_insert_outcome_conn` only.

### Design Decision D1 — Add `decided_by` parameter to `_insert_outcome_conn`

Change `_insert_outcome_conn` signature to accept `decided_by: str` and thread `"autofix"` from the call site at line 2050. Rationale:

- Matches the shape of every other outcome writer (parameter, not hardcoded literal).
- Keeps the provenance string next to the call site (readable — `AlertOutcome.AUTO_FIXED` and `"autofix"` are visually adjacent, easy to keep consistent).
- If a future stage differentiates auto-fix provenance (e.g., `"autofix-manual"`), the parameter is already there.

Alternative rejected: hardcode `"autofix"` inside `_insert_outcome_conn`. Cheaper by one line but inconsistent with sibling writers and hides the provenance choice from the caller.

### Design Decision D2 — Derive `initiated_by` from `approval.alert_id`, not from dry-run row

`execute_approved` at `orchestrator.py:1552` hardcodes `initiated_by="alert"` when calling `_claim_and_exec`.

Stage card says "The dry-run row already has the correct `initiated_by`; use it as source of truth." But the `ApprovalRecord` (from `approvals_repository.py:23-36`) does NOT carry `initiated_by`. Fetching the dry-run row just to read that column would require:
- A new repository method (`runs_repository.py` has no lookup-by-approval-id; only `.get(run_id)`).
- An extra DB round-trip inside the approval-execution critical path.

Better: `approval.alert_id` already encodes the same semantic. `execute_approved` at line 1538-1542 ALREADY uses `approval.alert_id is None` to distinguish operator-initiated (alert=None) vs alert-initiated (alert=loaded). The `runbook_runs.initiated_by` value of the dry-run is derived from the same `alert_id is None` check when the dry-run was recorded.

**Fix:** Change line 1552 to `initiated_by="operator" if approval.alert_id is None else "alert"`. One-line change, no new repository method, zero extra DB reads, single source of truth.

Alternative rejected: fetch the dry-run row (`self._runs.get(approval.dry_run_id)`) and read its `initiated_by`. Costs a DB round-trip and adds coupling for no semantic gain — both approaches derive from the same underlying invariant (`alert_id is None`).

### Design Decision D3 — Keep the `alert is not None` guard at line 2049

The guard's semantics are correct: `alert_outcomes` is a per-alert-lifecycle table. Its `alert_id` column FKs to `alerts`. An operator-initiated auto-fix run has no alert to reference — writing NULL would violate the FK, and even if the FK were widened, the analyzer's scorecards aggregate outcomes per-alert-dimension (source_tool, alertname, alertgroup) and an outcome with no alert cannot participate.

Consequence: the STAGE-009-013 prod E2E, which was alertless, could NEVER have written an outcome row regardless of D1's fix. Refinement's E2E MUST be **alert-linked** to validate the writer.

Alternative rejected: relax the guard and write outcomes for alertless operator runs. Would require making `alert_outcomes.alert_id` nullable (schema change) and would produce rows that no scorecard dimension can attribute. Cost is high, value is zero.

### Design Decision D4 — Refinement E2E is alert-linked (not the STAGE-009-013 pattern verbatim)

Refinement will diverge slightly from STAGE-009-013's pattern:

- STAGE-009-013 used an operator-triggered scratch runbook (no alert).
- STAGE-010-005 must use an alert-triggered scratch runbook, which requires an alert in the DB that matches the runbook's fingerprint.

**Approach:** create a scratch runbook + allow-list entry keyed to an alertname/fingerprint that either (a) already exists in the 14,390 prod alerts, or (b) is manufactured by direct DB insert for the E2E and cleaned up after. Trigger the auto-fix flow via the alert-dispatch path (or invoke `_execute_from_alert` directly via a dry-run trigger that points at the manufactured alert). Approve → real run → verify:
- `runbook_runs.initiated_by = 'alert'` (alert-triggered).
- `alert_outcomes` gets exactly one row with `outcome='auto_fixed'`, `decided_by='autofix'`, `alert_id=<manufactured>`.

Cleanup: delete the scratch runbook, allow-list entry, manufactured alert, and the resulting outcome row (or leave outcome as observational evidence + document in regression.md; decide during Refinement).

**Additional E2E to also validate on prod (D2 fix):** run a SECOND scratch runbook that IS operator-triggered (alertless), approve → real run. Verify `runbook_runs.initiated_by = 'operator'` (currently would be 'alert' before D2 fix). This exercises the `initiated_by` fix and gives us both attribution paths validated on prod in one session.
