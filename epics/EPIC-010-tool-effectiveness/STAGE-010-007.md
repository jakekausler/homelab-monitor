# STAGE-010-007: Fingerprint-overlap detection

## Status: Not Started

## Overview

Compute `alert_overlap_groups` rows so STAGE-010-006's `dedup_overlap` + `unique_share` metrics have a data source. Overlap = "two or more alerts share the same fingerprint within a ±5-minute window." Group_interval matches Alertmanager's default (`group_interval: 5m` per compose config).

Overlap detection is separate from scorecard aggregation because (a) it's deterministic given inputs (recomputable), (b) its output feeds MULTIPLE aggregation dimensions, (c) it's expensive enough that we don't want to recompute per-dimension.

## Concrete deliverables

1. Overlap-detection job under `kernel/analyzer/overlap.py` (or similar):
   - Runs nightly BEFORE `scorecard_aggregator` (STAGE-010-006) — sequencing enforced by declaring 007's job in the same `analyzer` concurrency group, and having 006 wait/read what 007 produced.
   - For each distinct fingerprint over the maximum aggregation window (90d), find all alerts with that fingerprint.
   - Cluster into groups by `opened_at` — alerts within ±5min of each other in the same cluster.
   - Write one `alert_overlap_groups` row per cluster: `fingerprint`, `group_key` (`<fingerprint>-<group_started_at_iso>`), `alert_ids` (JSON array), `group_started_at`, `computed_at`.
2. Idempotent writes: recomputes fresh groups per run; REPLACE by `(fingerprint, group_started_at)`.
3. Test coverage:
   - Two alerts with same fingerprint, opened 30s apart → one group with both alert_ids.
   - Two alerts with same fingerprint, opened 10min apart → two groups (each with one alert_id).
   - Alert with unique fingerprint → one group with just that alert_id.
   - Rerun with same alert set → identical group rows (verified by content, not timestamp).
   - Prod-scale test: 168k alerts + 85k unique fingerprints on a snapshot DB completes in < 60s.
