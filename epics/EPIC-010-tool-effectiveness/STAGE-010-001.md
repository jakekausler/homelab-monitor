# STAGE-010-001: SignatureWentSilent purge + rule removal

## Status: Complete 2026-07-06 (172,750 rows purged; 4-commit + push landed)

## Overview

Purge all `SignatureWentSilent` alerts from the `alerts` table (~158,782 rows on prod, ~94.5% of the population per 2026-07-05 recon) AND remove the vmalert rule that produces them. This is the epic's first stage because the noise dominates every dimension of the analyzer that comes later — filtering-at-analyzer hides the noise instead of fixing it. Explicit user sign-off recorded 2026-07-05 (planning session): "hard delete" chosen over archive/soft-delete options.

The underlying `homelab_log_signature_*` metric collection (from EPIC-004) is NOT touched; only the noisy alerting rule is deleted. If a future stage wants to re-enable signature-silent alerting with different thresholds, the metrics are still available.

**Retrofit for:** EPIC-004 (log pipeline / signature system).

## Concrete deliverables

1. Delete or comment-out the `SignatureWentSilent` rule from `deploy/vmalert/metrics/signature_silent.yaml` (or delete the entire file if it contains only this rule — verify during Design). Trigger vmalert `/-/reload` so the change takes effect without a container restart.
2. Emit an `audit_log` row BEFORE the delete, capturing the row count and reason. `who = "cli:stage-010-001-purge"` or the invoking session's principal. `what = "alerts_bulk_purged"`. `before = {alertname, row_count, source_tool, alertgroup}`. `after = null`.
3. `hm alerts purge --alertname=SignatureWentSilent --dry-run` CLI subcommand FIRST (shows count without deleting). Then `hm alerts purge --alertname=SignatureWentSilent --confirm-phrase="delete signature-silent noise"` executes the hard delete inside a single transaction (audit-log row + `DELETE FROM alerts WHERE alertname = 'SignatureWentSilent'`).
4. Regression test coverage:
   - `hm alerts purge` refuses without both `--alertname` and `--confirm-phrase` matching.
   - Confirm-phrase mismatch aborts with clear error.
   - Dry-run reports count without deleting.
   - Successful purge writes exactly ONE audit row + deletes exactly N alerts + does NOT touch other alertnames.
   - Idempotent second run: zero rows deleted, no audit row (or an audit row noting zero-count).
5. On prod (Refinement): verify existing SignatureWentSilent count (`SELECT COUNT(*) FROM alerts WHERE alertname='SignatureWentSilent'`), run the CLI with dry-run first, then execute the purge under supervision.

## Design Phase

**Status**: [x] Design (Complete 2026-07-06)

### Selected Approach (autonomous loop; recorded 2026-07-06)

The autonomous epic-stage loop selected the following approach after context gathering. Decisions align with EPIC-010's locked decisions (§Decision 4 sign-off on hard-delete) and with established repo patterns (audit-log helper, Alertmanager reloader, kill-switch confirm-phrase).

**A. vmalert rule file — DELETE entirely.**
`deploy/vmalert/metrics/signature_silent.yaml` contains ONE group (`signature_silent`) with ONE rule (`SignatureWentSilent`). Deleting the file is cleaner than commenting-out (which leaves an empty groups list). No other rules in the file to preserve.

**B. `hm alerts purge` CLI — NARROW scope.**
New top-level `hm alerts` subcommand shell registered in `apps/monitor/homelab_monitor/cli/main.py`. Only `purge` is exposed this stage. `hm alerts backfill-outcomes` (STAGE-010-004) will hang off the same shell later. Args:
- `--alertname=NAME` (required; validated non-empty)
- `--dry-run` (optional; reports count without deleting or writing audit)
- `--confirm-phrase=PHRASE` (required for real run; ignored in dry-run)
Refuses if BOTH `--dry-run` and `--confirm-phrase` are omitted (must pick one mode).

**C. Confirm-phrase text — `"delete signature-silent noise"`.**
Case-fold match (`str.strip().casefold() == expected.strip().casefold()`), mirroring `PhraseMatchMode.CASE_FOLD` from `apps/monitor/homelab_monitor/kernel/security/pin.py`. CLI adaptation of the STAGE-009-007 kill-switch pattern: on mismatch, print `confirm_phrase must equal 'delete signature-silent noise'` to stderr and exit code 1 (no `HTTPException`, no PIN, no rate-limiter).

**D. Scope — narrow.**
Only SignatureWentSilent purge + `signature_silent.yaml` deletion. No opportunistic auditing of other rules or alertnames. Any additional cleanup opportunities that surface during Refinement file to `epics/EPIC-010-tool-effectiveness/regression.md` (created lazily if absent), NOT this stage.

**E. vmalert `/-/reload` — runtime code (new `VmalertReloader` helper).**
Build `VmalertReloader` in `apps/monitor/homelab_monitor/kernel/vmalert/reload.py` (new module), mirroring the shape of `AlertmanagerReloader` in `alertmanager/render.py`:
- POST `http://vmalert-metrics:8880/-/reload` (no auth, internal-only)
- `httpx.Timeout(5.0, connect=2.0)`
- Warn-on-failure semantics: log a warning but return `False` on network/HTTP failure; do NOT raise
- Return `True` on 2xx, `False` otherwise
The CLI calls `VmalertReloader().reload()` AFTER commit; a failed reload prints a warning to stderr but returns exit code 0 (vmalert's `-configCheckInterval=30s` auto-picks up file changes within 30s regardless). Matches STAGE-010-012's future Apply-action pattern for rule mutations. Also puts a reusable helper in place for STAGE-010-012.

**F. `alertname` filter SQL — JSON-extract path (SCHEMA CORRECTION).**
Discovery during Design context-gathering: `alertname` is NOT a top-level column on the `alerts` table (verified against `alembic/versions/0001_initial_schema.py` + `0005_alerts_columns.py` — columns are `id`, `fingerprint`, `created_at`, `source_tool`, `severity`, `status`, `opened_at`, `last_seen_at`, `resolved_at`, `ack_at`, `ack_by`, `runbook_id`, `payload_json`). `alertname` lives inside `payload_json` at `$.labels.alertname` (see `AlertRepository._row_to_alert`). SQL therefore uses SQLite's JSON1 `json_extract`:
- Count: `SELECT COUNT(*) FROM alerts WHERE json_extract(payload_json, '$.labels.alertname') = :alertname`
- Delete: `DELETE FROM alerts WHERE json_extract(payload_json, '$.labels.alertname') = :alertname`
Full table scan is acceptable for this one-shot purge (~168k rows → ~10k residual). This correction supersedes the SQL literal shown in the original stage-card deliverables.

**Order of operations inside single transaction:**
1. `SELECT COUNT(*)` — captures pre-delete row count (bound to audit `before` payload)
2. `INSERT INTO audit_log` via `insert_audit(conn, who="cli:stage-010-001-purge", what="alerts_bulk_purged", before={"alertname": "SignatureWentSilent", "row_count": N, "source_tool": "vmalert-metrics", "alertgroup": "signature_silent"}, after=None)`
3. `DELETE FROM alerts WHERE json_extract(...) = :alertname`
4. Commit
5. Post-commit: call `VmalertReloader().reload()` (non-blocking on failure)

**Idempotent second run:** dry-run reports 0. Real run with 0 matches STILL writes an audit row with `row_count=0` — explicit "attempted, found nothing" audit trail matches the auto-fix safety model (`project_autofix_safety_model.md`). Deleting from an empty match set is a no-op DELETE (0 rows changed).
