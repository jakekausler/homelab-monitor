# STAGE-010-002: Schema evolution — scorecards + new outcome enums + new supporting tables

## Status: Complete

## Overview

Alembic migration 0052 that lands ALL the DB schema changes EPIC-010 needs, in one migration so downstream stages don't ping-pong. Expands the `tool_scorecards` scaffold (which shipped as a stub in migration 0001) to hold multi-dimensional scorecard rows. Extends `AlertOutcome` enum with `AUTO_RESOLVED` and `MAINTENANCE_SUPPRESSED` values. Creates four new tables: `alert_overlap_groups`, `shadow_rule_results`, `recommendations`, `rule_annotations`.

Per EPIC-010 Decision 1 the analyzer aggregates across FIVE orthogonal dimensions (`source_tool`, `category`, `target_kind`, `alertgroup`, `alertname`) × three windows (7d / 30d / 90d), so the `tool_scorecards` primary key must reflect that.

## Concrete deliverables

1. Alembic migration `0052_epic010_scorecards_and_outcomes.py`:
   - Drop the stub `tool_scorecards` table + recreate with the real column set: `id`, `dimension` (TEXT NOT NULL — one of `source_tool` / `category` / `target_kind` / `alertgroup` / `alertname`), `dimension_value` (TEXT NOT NULL), `window` (TEXT NOT NULL — one of `7d` / `30d` / `90d`), `alerts_emitted` (INTEGER NOT NULL), `action_rate` (REAL NOT NULL), `dedup_overlap` (REAL NOT NULL), `unique_share` (REAL NOT NULL), `computed_at` (TEXT NOT NULL). UNIQUE INDEX on `(dimension, dimension_value, window)`.
   - New table `alert_overlap_groups`: `id`, `fingerprint` (TEXT NOT NULL), `group_key` (TEXT NOT NULL — synthetic identifier for the ±5min overlap window), `alert_ids` (TEXT NOT NULL — JSON array), `group_started_at` (TEXT NOT NULL), `computed_at` (TEXT NOT NULL). INDEX on `(fingerprint, group_started_at)`.
   - New table `shadow_rule_results`: `id`, `pair_name` (TEXT NOT NULL), `window` (TEXT NOT NULL), `rule_a_hits` (INTEGER NOT NULL), `rule_b_hits` (INTEGER NOT NULL), `both_hits` (INTEGER NOT NULL), `either_hits` (INTEGER NOT NULL), `disagreement_count` (INTEGER NOT NULL), `computed_at` (TEXT NOT NULL). UNIQUE INDEX on `(pair_name, window)`.
   - New table `recommendations`: `id`, `dimension`, `dimension_value`, `rule_name` (TEXT NOT NULL — the predicate that triggered), `message` (TEXT NOT NULL — human-readable), `severity` (TEXT NOT NULL — `info` / `warning` / `action-required`), `status` (TEXT NOT NULL — `pending` / `applied` / `dismissed` / `snoozed`), `created_at` (TEXT NOT NULL), `decided_at` (TEXT), `decided_by` (INTEGER, FK users.id), `applied_action_id` (TEXT — nullable, references an Apply action). INDEX on `(status, created_at)`.
   - New table `rule_annotations`: `id`, `annotation_kind` (TEXT NOT NULL — `known_noisy` / other kinds added later), `target_source_tool` (TEXT), `target_alertgroup` (TEXT), `target_alertname` (TEXT), `note` (TEXT), `created_at` (TEXT NOT NULL), `created_by` (INTEGER, FK users.id). One of `target_alertname` / `target_alertgroup` / `target_source_tool` must be non-null (CHECK constraint).
   - Down-migration reverses cleanly.
2. Extend `AlertOutcome` StrEnum in `apps/monitor/homelab_monitor/kernel/alerts/types.py` with:
   - `AUTO_RESOLVED = "auto_resolved"` — alert transitioned to Alertmanager resolved state without any user action.
   - `MAINTENANCE_SUPPRESSED = "maintenance_suppressed"` — alert fired within an active maintenance window (writer lands in EPIC-012, but the enum value must exist now so the DB constraint is settled).
3. Update pydantic models exposed via API for scorecards + recommendations, so the shapes are locked before subsequent stages consume them.
4. Test coverage:
   - Migration up + down (existing `test_db_migrations.py` pattern).
   - All new tables' schemas match the DDL.
   - `AlertOutcome` enum contains the new values + existing writer paths still work.
   - Attempt to insert a `tool_scorecards` row with a duplicate `(dimension, dimension_value, window)` fails with UNIQUE violation.
   - `rule_annotations` CHECK constraint rejects rows with all three `target_*` columns null.

## Design Notes

**Design decision (autonomous — epic-loop directive):** Selected A1 — single Alembic migration `0052_epic010_scorecards_and_outcomes.py` that (a) drops+recreates `tool_scorecards` with the 5-dim × 3-window shape, (b) creates 4 new tables (`alert_overlap_groups`, `shadow_rule_results`, `recommendations`, `rule_annotations`), (c) reverses cleanly (down-migration restores the 3-column stub of `tool_scorecards` per `0001_initial_schema.py`). Chosen by the implementing session (autonomous loop — Design decisions are mechanical for this stage; every column/type/constraint is pre-locked by handoff + Epic LOCKED DECISIONS 1, 5, 7). No brainstormer invoked — no architectural choice space.

**Locked mechanical decisions:**
- `revision = "0052"`, `down_revision = "0051"`
- Column type convention: TEXT for string/enum/timestamp, INTEGER for counts/FKs, REAL for ratios (matches migrations 0001–0051)
- FK targets: `users.id` for `recommendations.decided_by` and `rule_annotations.created_by`
- CHECK constraint on `rule_annotations`: `CHECK (target_source_tool IS NOT NULL OR target_alertgroup IS NOT NULL OR target_alertname IS NOT NULL)`, named `ck_rule_annotations_target_nonnull`
- `AlertOutcome` StrEnum in `apps/monitor/homelab_monitor/kernel/alerts/types.py` extended with `AUTO_RESOLVED = "auto_resolved"` and `MAINTENANCE_SUPPRESSED = "maintenance_suppressed"` (backward-compatible — all existing writer paths use existing members)
- Pydantic API models for scorecards + recommendations added to `apps/monitor/homelab_monitor/kernel/api/schemas.py` (co-located with existing models — no new `api/models/` package; premature abstraction avoided)
- `apps/monitor/tests/test_db_migrations.py`: `EXPECTED_TABLES` set extended with the 4 new tables; new test functions cover up/down reversibility, UNIQUE on `tool_scorecards(dimension, dimension_value, window)`, UNIQUE on `shadow_rule_results(pair_name, window)`, CHECK on `rule_annotations`, and `AlertOutcome` new-member availability
- Non-destructive to prod data — no rows migrated, only additive DDL + stub-table drop (stub is dead code: no reader/writer in the codebase)

**Stage consistency check:** ✅ description matches criteria, no copy-paste artifacts, all deliverables covered. **Backend contract verification:** N/A (backend schema stage, no frontend integration). **Testability check:** N/A (not a create/add UI feature). **Look-ahead:** unblocks STAGE-010-003 (Karma reconcile → AUTO_RESOLVED), 004 (backfill), 006/007 (scorecards+overlap), 008 (API), 009/010 (shadow rules), 011/012 (recommendations+annotations); EPIC-012 (MAINTENANCE_SUPPRESSED writer).

## Refinement Notes

Applied migration `0052_epic010_scorecards_and_outcomes.py` against a `.backup`-copy of the production DB (798 MiB, WAL mode, alembic revision 0051 at snapshot time). All 13 gates PASS:

- Upgrade `0051 → 0052` succeeded via `hm migrate` (routes through kernel `_build_config`).
- Post-upgrade schema: 9-col `tool_scorecards` + 4 new tables (`alert_overlap_groups`, `shadow_rule_results`, `recommendations`, `rule_annotations`). All 4 indexes present with correct names; `rule_annotations.ck_rule_annotations_target_nonnull` CHECK constraint intact; `recommendations.decided_by` FK to `users.id` intact.
- Prod data preserved: `alerts=14109`, `users=1`, unchanged through the entire up→down cycle.
- Downgrade `0052 → 0051` succeeded via a small Python driver reusing `_build_config` (raw `alembic downgrade -1` from shell does not work in this repo — see below).
- Post-downgrade schema: stub 3-col `tool_scorecards` (id, tool, created_at) restored; all 4 new tables dropped.

**Migration NOT applied to live prod this stage.** It deploys as part of a normal prod redeploy in a later stage.

**Non-blocking findings for the epic regression list** (also filed in `regression.md`):
1. Raw `alembic upgrade head` / `alembic downgrade -1` from shell against a copy DB fails with `NoSuchModuleError: Can't load plugin: sqlalchemy.dialects:driver` because `apps/monitor/alembic.ini` has a placeholder `sqlalchemy.url = driver://...` and `env.py` reads it verbatim rather than consuming `HOMELAB_MONITOR_DB_URL` or `-x url=...`. Workaround: use `hm migrate` or a Python driver that calls `_build_config`.
2. The DB URL scheme must be `sqlite+aiosqlite://` (not plain `sqlite://`) because `env.py` uses `async_engine_from_config`.
