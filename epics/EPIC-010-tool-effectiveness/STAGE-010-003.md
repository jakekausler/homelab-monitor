# STAGE-010-003: Karma → outcome retrofit (periodic reconciliation)

## Status: Not Started

## Overview

Prod-DB recon 2026-07-05 confirmed `alert_outcomes` is EMPTY (0 rows) despite 168k `alerts` rows. Root cause: Karma (the embedded alert-lifecycle UI) posts ack/silence actions directly to Alertmanager, never touching our monitor. Every alert Jake has acknowledged in the past ~7 weeks is invisible to the analyzer.

Per EPIC-010 Decision 2 (locked 2026-07-05), fix via periodic pull from Alertmanager rather than proxy interception: hourly scheduled job pulls `/api/v2/silences` + resolved-alert state, matches each silence/resolution to `alerts.fingerprint`, writes `AlertOutcome.ACKED` / `AlertOutcome.AUTO_RESOLVED` rows to `alert_outcomes`. Idempotent (INSERT OR IGNORE on `(alert_id, outcome)`) so re-runs never double-count.

**Retrofit for:** EPIC-001..009 + 017 (all completed epics that emit alerts).

## Concrete deliverables

1. New collector `karma_outcome_reconciler` under `apps/monitor/homelab_monitor/plugins/collectors/builtin/` (or `kernel/analyzer/` — decide during Design):
   - `interval: 1h`, `concurrency_group: analyzer`, `run_kind: ASYNC`, `timeout: 5m`.
   - Pulls `GET /api/v2/silences` from AM (auth: Alertmanager doesn't require auth in our compose — verify).
   - Pulls `GET /api/v2/alerts?resolved=true` (or equivalent) for alerts that have transitioned to resolved.
   - For each silence with matcher(s) that resolve to a specific `alerts.fingerprint` in our DB (matcher shape: label-value pairs; use the fingerprinting.py:21 same-algorithm to compute what the target fingerprint SHOULD be): write `AlertOutcome.ACKED` with `decided_by = "karma"`, `decided_at = silence.created_at`.
   - For each alert that transitioned to `resolved_at IS NOT NULL` since last successful reconciliation AND has NO `alert_outcomes` row yet: write `AlertOutcome.AUTO_RESOLVED` with `decided_by = "reconciler"`.
   - Records last successful reconciliation timestamp in a new `app_settings` key `analyzer.last_reconciliation_at` to bound the incremental scan window.
2. Idempotency: use `INSERT OR IGNORE INTO alert_outcomes (alert_id, outcome, ...) VALUES ...` — the natural UNIQUE key is `(alert_id, outcome)` (add index in this stage's migration OR piggyback on STAGE-010-002 by adding it there — decide in Design).
3. Match semantics: for silences with LABEL matchers (Karma's default) — reconstruct the label set and compute the fingerprint using `fingerprinting.py:compute_fingerprint`. For silences with FINGERPRINT matchers (rare) — use directly. Silences that don't uniquely resolve to ONE `alerts` row are logged and skipped (not an error — just noise).
4. Handles Alertmanager unavailability gracefully: if AM is unreachable, log + emit `homelab_collector_run_last_error_age_seconds`, don't crash, retry next tick.
5. Test coverage:
   - Silence with fingerprint matcher → writes ACKED row.
   - Silence with label matcher that resolves to one alert → writes ACKED row.
   - Silence with label matcher that resolves to multiple alerts → skipped with warning log.
   - Silence with label matcher that resolves to zero alerts → skipped silently.
   - Alert resolved between two reconciliation ticks → writes AUTO_RESOLVED row.
   - Re-run with same AM state → zero new rows written (INSERT OR IGNORE succeeds silently).
   - AM 503 / connection refused → collector run marked errored, no partial writes, next tick retries.
